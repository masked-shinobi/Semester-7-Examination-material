1. The big idea: Fault → Error → Failure

A computer system should do its job correctly for a given period of time. But parts (hardware and software) can have problems. Those problems travel in three steps:

Fault
the root defect
→
Error
wrong data appears
→
Failure
wrong service to the user
Example: a serverFault: the hard disk develops a defect. Error: wrong data is read from it. Failure: the server gives the user incorrect service.
Goal of fault-tolerant designPrevent, detect, contain, mask or recover from faults, so a fault does not become a failure.
Everyday pictureA tiny crack in a water pipe (fault) → a little water leaks (error) → the room floods (failure).

2. Failure rate, λ(t)

DefinitionFailure rate is how quickly a part fails at a particular moment, given that it has survived until that moment. Symbol: λ(t). Unit: failures per hour (1/hour).

Why “given that it survived”? A 10-year-old bulb that is still glowing is judged only against bulbs that also lasted 10 years. That makes it a conditional measure.

Failure rate function
λ(t) = f(t) / R(t)
T = time to failure, f(t) = probability density of failure (how likely failure is around time t), R(t) = reliability at time t.

Constant failure rate

For simple calculations we assume λ never changes: λ(t) = λ. Then reliability follows the exponential reliability model:

R(t) = e−λt
How to read λλ = 0.001 failures/hour means the failure intensity is 0.001 per hour. It does not mean exactly 0.001 failures happen every hour.

The Bathtub Curve

DefinitionA graph of failure rate over a component’s whole life. It has three regions and looks like a bathtub.
  • Region 1 – Early failure (infant mortality): rate starts high and drops. Causes: manufacturing defects, design defects, installation errors, weak parts from the start.
  • Region 2 – Useful life: rate is about constant, λ(t) ≈ constant. The exponential model R(t) = e−λt is used here. Failures are mostly random.
  • Region 3 – Wear-out: rate rises with time. Causes: aging, physical wear, material degradation, thermal (heat) stress, mechanical deterioration.
Everyday pictureA new phone: some are faulty from the factory (early), most work fine for years (useful life), then the battery and buttons wear out (wear-out).

3. Reliability, failure probability and how they connect

Reliability R(t)The probability that a system or component does its intended job, without failure, for a stated time, under stated operating conditions.

It is a probability, so 0 ≤ R(t) ≤ 1 (or 0% to 100%).

Reliability function
R(t) = P(T > t)
Meaning: the chance that the system is still working after time t.
Example: reliability after 100 hours with λ = 0.001/hourR(100) = e−0.001×100 = e−0.1 ≈ 0.9048, so reliability ≈ 90.48%. There is about a 90.48% chance it runs 100 hours without failing (under the constant-failure-rate model).
Failure probability F(t)The probability that the item has failed by time t. It is the opposite (complement) of reliability.
F(t) = 1 − R(t)
F(t) = 1 − e−λt (constant λ)
ExampleR = 0.9048 → F = 1 − 0.9048 = 0.0952 = 9.52%.

Link between failure rate and reliability

R(t) = e−∫₀ᵗ λ(u) du
If λ is constant this becomes R(t) = e−λt. The integral simply “adds up” the failure rate over time. This link is very important in reliability work.

4. MTTF, and MTTF vs MTBF

MTTF – Mean Time To FailureThe expected running time of a non-repairable part before its first failure. Measured in hours, days or years.
General formula
MTTF = ∫₀^∞ R(t) dt
For constant failure rate
MTTF = 1 / λ   and   λ = 1 / MTTF
Exampleλ = 0.0001/hour → MTTF = 1 / 0.0001 = 10,000 hours.
Careful10,000 hours does not mean every part dies at exactly 10,000 hours. It is an average.

5. Canonical structures: series and parallel

Canonical structureA standard way of arranging components to show how they depend on each other, for reliability analysis. The two basic ones are series and parallel; bigger systems are built from them.

Series structure

DefinitionEvery component must work for the system to work.
Rs = R1 × R2 × R3 × … × Rn = Π Ri
(components must be statistically independent)
ExampleR1 = 0.9, R2 = 0.8 → Rs = 0.9 × 0.8 = 0.72 = 72%.
Ten components, each 0.99: Rs = (0.99)10 ≈ 0.904. So adding more components in series generally lowers reliability.
Everyday pictureOld festival lights: if one bulb goes, the whole string goes dark.

Parallel structure

DefinitionThe system keeps working as long as at least one component (path) still works.

Here A works while B has failed, so the system still operates.

Rp = 1 − [(1−R1)(1−R2)…(1−Rn)]
Two identical components:
Rp = 1 − (1−R)²
ExampleR = 0.9 for each → Rp = 1 − (0.1)² = 1 − 0.01 = 0.99 = 99%. The system fails only if both fail.
SeriesParallel
All components must workAt least one path must work
One failure can fail the systemSystem may survive one failure

6. Redundancy and resilient structures

RedundancyAdding extra resources beyond the minimum needed, so the system can tolerate faults. Example: one CPU becomes CPU1, CPU2, CPU3.

Four types

1. HardwareExtra hardware, e.g. three processors doing the same computation.
2. InformationExtra data to detect or correct errors: parity bits, error-correcting codes, check bits.
3. SoftwareSeveral software versions, to survive software faults.
4. TimeRepeat the operation to catch or overcome temporary (transient) faults.

Resilient structure

DefinitionA design that uses redundancy plus fault-tolerance mechanisms so the system keeps giving its required service despite specified faults.

7. Reliability evaluation techniques

Reliability evaluationWorking out (or estimating) the probability that a system performs its required function for a given time under given conditions. It gets harder as systems get complex. Four common techniques: RBD, Fault Tree Analysis, Cut-Set Analysis, Markov Analysis.

Reliability Block Diagram (RBD)

DefinitionA picture of the system’s working structure: blocks are components, and the connections show what must work for the system to work.

Series RBD [A]–[B]–[C]: all blocks must work, Rs = RA × RB × RC. Parallel RBD [A] and [B] side by side: at least one path must work, Rp = 1 − (1−RA)(1−RB). (Use the series and parallel pictures from section 5.)

Fault Tree Analysis (FTA)

DefinitionA top-down method. Start from a bad outcome (the Top Event) and find which combinations of lower-level faults can cause it.
AND gateOutput happens only if all inputs happen.
P(A AND B) = P(A) × P(B)
(independent events)
OR gateOutput happens if any one input happens.
P(A OR B) = 1 − (1−P(A))(1−P(B))
(independent events)

Cut set and minimal cut set

Cut setA set of component failures that is enough to make the system fail.
ExampleIf A alone or B alone can fail the system, then {A} and {B} are cut sets.
Minimal cut setA cut set with nothing extra: remove any member and it no longer causes failure.
ExampleThe system fails only when both A and B fail. Then {A, B} is a minimal cut set (since neither A nor B alone causes failure).

Markov analysis

DefinitionA state-based method. The system is shown as a set of states (e.g. Working, Failed), and the moves between states have rates. Best when a system has several states and repair or recovery matters.

8. Processor-level fault tolerance

DefinitionUsing redundancy, fault detection, fault masking and recovery at the processor level, so the system stays correct despite a processor fault.
Processor fault
→
Wrong computation
→
Wrong output
→
System failure

Duplex system (2 processors)

DefinitionTwo processors do the same work and a comparator checks that their outputs agree.
  • Agree: CPU1 = 50, CPU2 = 50 → 50 = 50 → output accepted.
  • Disagree: CPU1 = 50, CPU2 = 60 → mismatch → error detected.
LimitationWe know they disagree, but from two outputs alone we generally cannot tell which processor is wrong.

Triple Modular Redundancy (TMR)

DefinitionThree modules do the same job and a majority voter picks the value given by at least two of them.

CPU2 is faulty and says 250. The voter sees 100, 250, 100 → majority is 100 → output 100. The wrong value is masked.

Fault maskingStopping a fault’s effect from reaching the system output, using redundancy or other mechanisms. TMR is the key example.

N-modular redundancy (NMR)

DefinitionN modules do the same job and a voting mechanism decides the output.
Faulty modules tolerated (odd N, ideal voting, reliable voter)
(N − 1) / 2
N = 3 → (3−1)/2 = 1. N = 5 → (5−1)/2 = 2.

Fault detection vs fault masking

Fault detectionFault masking
What it doesNotices something is wrongHides the effect of the fault
Example50 vs 60 → mismatch50, 60, 50 → majority 50 → output 50
Used byDuplexTMR (one faulty CPU, under its assumptions)

10. Byzantine failures

Byzantine failureA faulty component can behave in any way: give wrong results, or give different or conflicting information to different parts of the system. One of the hardest failure models in distributed systems.
ExampleCPU1 is faulty. It tells CPU2 “Result = 100” but tells CPU3 “Result = 200”. Now CPU2 believes 100 and CPU3 believes 200.

A Byzantine faulty part may…

  • produce incorrect results;
  • send different results to different components;
  • change its behaviour over time;
  • look correct to some components;
  • behave wrongly toward others;
  • give arbitrary responses.

Crash failure vs Byzantine failure

Crash failureA component simply stops and gives no more service. Easy, because it never sends conflicting information afterwards.
CrashByzantine

The Byzantine Generals Problem

DefinitionA distributed agreement problem: correct participants must reach one consistent decision even though some participants are faulty and may send arbitrary or conflicting information.
StorySeveral generals must decide: ATTACK or RETREAT. Some are traitors. A traitor might tell General A “ATTACK” and General B “RETREAT”. The loyal generals must still agree, according to the protocol’s assumptions.

Byzantine agreement: 3 goals

1. AgreementCorrect participants never make conflicting decisions.
2. ValidityThe decision meets the required validity condition when the protocol’s assumptions hold.
3. TerminationCorrect participants eventually reach a decision.

11. Limits of redundancy (very exam-friendly)

Redundancy is not magicRedundancy helps fault tolerance and, under suitable assumptions, reliability. But it adds extra parts (voters, comparators, switching circuits, interconnections) that can fail too. So extra redundancy does not automatically give unlimited reliability. Evaluate the complete architecture.

The voter

In TMR the voter picks the majority (A, A, B → A). But it is a critical part: unless it is protected, the voter can be a single point of failure.

Common-cause failures

DefinitionOne underlying cause hits several redundant components at once.
Key pointRedundancy works best when the redundant units are sufficiently independent.

Independence of failures

Series and parallel formulas (multiplying probabilities) assume component failures are statistically independent. If CPU1, CPU2 and CPU3 share one power supply, that assumption is broken, and the simple formulas may not match the real reliability.

One-line definitions

  • Failure rate: instantaneous rate of failure given survival so far.
  • Reliability: probability of working without failure for a given time and conditions.
  • MTTF: expected time to first failure of a non-repairable item.
  • Canonical structure: standard arrangement showing component relationships.
  • Series: every component must work.
  • Parallel: one working path is enough.
  • Redundancy: extra resources beyond the minimum.
  • Resilient structure: keeps service despite specified faults.
  • Reliability evaluation: estimating probability of successful operation.
  • RBD: diagram of functional relationships among components.
  • Fault tree analysis: top-down search for fault combinations causing a top event.
  • Cut set: failures enough to fail the system.
  • Minimal cut set: cut set with no unnecessary member.
  • Processor-level FT: redundancy and fault handling at the processor level.
  • Duplex: two processors compared to detect disagreement.
  • TMR: three modules and a majority vote, tolerating one faulty module.
  • Fault masking: keeping a fault’s effect away from the output.
  • Standby redundancy: backups activated when the active unit fails.
  • Byzantine failure: arbitrary or conflicting behaviour by a faulty component.

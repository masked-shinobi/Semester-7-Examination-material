1. Why software needs fault tolerance

Fault tolerance means the system keeps working correctly even when something inside it is broken. A bug (defect) is a mistake in the code.

Two kinds of difficulty make correct software hard:

  • Essential difficulty – the problem itself is complex. The software must handle a huge number of states with tricky rules for moving between them, and it keeps changing (new features, new hardware, new operating systems).
  • Accidental difficulty – plain human mistakes in the code.

We first try hard to reduce bugs by testing. But testing can never remove every bug, so we add fault-tolerance techniques to limit the damage of the bugs that remain.

Big picture: Step 1 detect a problem (acceptance tests). Step 2 survive it, using one copy of the software made stronger (single-version), many copies (N-version), or backups (recovery block). Step 3 measure how reliable the software is (reliability models).

2. Acceptance tests – noticing that something is wrong

To tolerate a fault you must first detect it. An acceptance test is simply a “does this look reasonable?” check on the output. Three common types:

a) Timing check

If you roughly know how long the code should take, set a watchdog timer. If the timer rings before the code finishes, assume a failure. It can run alongside other tests.

b) Verification of output

Some problems are hard to solve but easy to check.

Example: a jigsaw puzzle takes ages to solve, but one glance tells you it is done. Same with: square root (square the answer, do you get the number back?), factorization (multiply the factors), equations (put the answer back into the equation).

c) Range check

When there is no neat way to verify, use what you know to set allowed limits. Anything outside is declared an error. Limits can be fixed, or a simple function of the inputs.

Example: a satellite takes temperature pictures of the Earth. We set a sensible temperature range; a reading outside it is treated as an error.

Setting the limits: sensitivity vs specificity

TermSimple meaningFormal meaning
SensitivityHow good the test is at catching wrong outputsP(test says “error” | output really is wrong)
SpecificityWhen the test shouts “error”, how often is it truly an errorP(output really wrong | test says “error”)
False alarmTest blames a perfectly good outputP(test says “error” | output is correct)
Think of a smoke alarm: high sensitivity = it always rings for real fires. Low specificity or many false alarms = it also rings when you make toast. Tight limits catch more errors but cause more false alarms, so you must balance them.

3. Single-version fault tolerance: one program, made tougher

Wrappers

A wrapper is extra software placed around a program, like a security guard at a door. It checks everything going in and everything coming out. It can wrap application software, middleware, or even an OS kernel.

Why wrappers became popular: people started using COTS (Commercial Off-The-Shelf) software, meaning ready-made general-purpose components. For them an error is “an annoyance, not a calamity”, so they are not safe enough for high-reliability jobs. A wrapper blocks inputs that are out of range or known to cause errors, and passes outputs through an acceptance test. If the test fails, the system is told and decides what to do.

Wrappers are specific to the program and system they guard. Uses:

  • Buffer overflow. C does not check array limits. A buffer is a small box of memory; writing a long string into it spills over and overwrites other memory (by accident or by an attacker). The wrapper checks the buffer is big enough before copying.
  • Checking a scheduler. EDF (Earliest Deadline First): always run the ready task whose deadline is nearest. The wrapper checks the scheduler really picks that task and that a newly arrived task with an earlier deadline pre-empts (interrupts) the running one. (Some tasks cannot be interrupted at certain points.)
  • Software with known bugs. Suppose testing shows it fails for a set of inputs S. The wrapper checks each input: not in S → forward it; in S → raise an exception, or send it to custom backup code that handles S.
  • Checking output. Every output goes through an acceptance test: pass → release; fail → raise an exception.
A wrapper works well only if: (1) the acceptance test is good; (2) you can see inside the component. A “black box” only shows outputs, so a scheduler wrapper is impossible without knowing task deadlines; (3) the component has been well tested, so you know which inputs fail.

4. Software rejuvenation – “turn it off and on again”

When your PC hangs you reboot it. That is software rejuvenation. Over time a running process keeps grabbing memory and file locks without releasing them, and uncorrected errors pile up in its data, until it breaks. Rejuvenation proactively stops it, cleans its state, and restarts it before that happens.

Level: how much to restart

  • Application level – suspend one application, clean up (garbage collection, reset data structures), restart it.
  • Processor level – reboot the whole processor; affects every application on it.

Choose the level where the resources are actually worn out.

Timing: when to restart

Time-based: restart at fixed intervals. Too often wastes time; too rarely lets errors hurt. We balance this using a model. Notation:

Ñ(t)expected number of errors in time t without rejuvenation
Cecost of each error
Crcost of each rejuvenation
Ptime between rejuvenations

Total cost over one period, then cost per unit time:

C_rejuv(P) = Ñ(P)·Ce + Cr
C_rate(P) = C_rejuv(P)/P = (Ñ(P)·Ce + Cr)/P

Three cases for how errors grow:

Error behaviourÑ(P)Result
Constant error rate λλPC_rate = λCe + Cr/P. Smallest when P = ∞, so never rejuvenate. It only helps when errors increase with time.
Errors grow with time (squared)λP²C_rate = λP·Ce + Cr/P. Set the slope to zero: P* = √(Cr / (λCe))
Errors grow faster (power n)λPⁿC_rate = λPⁿ⁻¹Ce + Cr/P. P* = (Cr / ((n−1)λCe))^(1/n)
Reading the graph (Fig. 2 in your slides): it plots the best period P* against n for different Cr/Ce ratios (0.05 to 0.40, λ = 1). A costlier rejuvenation (bigger Cr/Ce) means you should restart less often.

Prediction-based: watch the system (memory used, file locks held…), predict when it will fail, and rejuvenate just before the predicted crash.

Example: a process eats memory at a steady speed, so you can calculate when memory runs out and restart just before.

This needs enough status information. Inside an OS it is easy to get; a normal add-on package can only use what the OS offers. Linux tools: vmstat (CPU, memory, paging, traps, I/O), iostat (CPU % at user/system level, usage per I/O device), netstat (network connections, routing tables, interfaces), nfsstat (network file server statistics). Collect data, spot trends, predict errors.

5. Data diversity – “try a slightly different input”

The input space is every possible input a program can receive. Part of it is the failure region (inputs that make the program fail); the rest is safe. The program fails if and only if the input lies in the failure region. Real input spaces have many dimensions; we draw 2.

Both have the same fraction of failing inputs. But in (a) a tiny nudge to the input moves it out of a black spot into a safe area; in (b) a small nudge doesn’t help. For case (a), we perturb (slightly change) the input and hope it lands in a safe region. This is data diversity.

  • Explicit perturbation: add a small deviation to some inputs.
  • Implicit perturbation: collect inputs in a way that makes them naturally slightly different.
Example: a controller reads pressure and temperature of a refrigerator every second as (pi, ti). Physics says one second’s values are close to the previous second’s. If (pi, ti) crashes the program, try (pi−1, ti) instead.

SIHFT – Software Implemented Hardware Fault Tolerance

Data diversity + time redundancy (do the work twice, at different times) can detect hardware faults using software only. It is a cheap option, ideal for COTS processors that have no error detection.

Method (integer programs): make a second program where every variable and constant is multiplied by a diversity factor k. Its final results should be exactly k × the original results. Run both on the same hardware; if the results don’t match, hardware is faulty. Hardware faults hit the two runs differently, depending on k.

Example – stuck-at-0 bus: a bus is a set of wires; bit i is stuck at 0. If the data’s bit i is 1, it arrives wrong. With k = 2, that bit moves to wire i+1, which is fine, so the two runs differ and the fault is caught. It is missed only if bits i and i−1 are both 0, which has probability 0.25. With k = −1, most 0s turn into 1s, so the chance of missing it is much lower.
  • Choosing k: big enough to detect faults often, small enough to avoid overflow/underflow (number too big or small to store). If the program uses bitwise XOR/AND, use k = 2l (l an integer), since multiplying then is a simple bit shift.
  • Even k = −1 can overflow if a variable holds the most negative number (two’s complement). Fix: use a bigger integer type for that variable. Range analysis finds which variables need it. The transformation is simple and can be automated.
  • Slide example (k = 2): original: x=3, y=1, while (i<5) {y = y*(x+i); i = i+2}. Transformed: x=6, y=2, while (i<10) {y = y*(x+i)/2; i = i+4}. Final z is doubled.

RESO – Recomputing with Shifted Operands

Like SIHFT, but the hardware itself is modified. Each arithmetic/logic unit first computes on the original operands, then again on shifted operands (k = 2l only). Overflow is easier to avoid because the hardware can simply have extra bits.

Steps: (1) add X and Y unshifted, store result Z in the register. (2) shift X and Y, add them. (3) shift that result back the opposite way. (4) the checker compares it with the register; a mismatch means a hardware fault.

6. N-version programming – many teams, one vote

N independent teams write software from the same specification. All N versions run in parallel and their outputs are voted on. Hope: independent teams are unlikely to make the same bug.

Probability: if each version is buggy with the same probability q, independently, the chance that at most m of N versions are defective is:

p_ind(N,m,q) = Σ (i = 0 to m) C(N,i) · qⁱ · (1−q)^(N−i)

(C(N,i) = “N choose i”, the number of ways to pick which i versions are bad.)

Problem 1: the consistent comparison problem

Even correct versions may not agree. Versions compute some value x and compare with a constant c. The comparison is consistent if all versions give x ≥ c, or all give x < c. Because teams use different algorithms, x differs slightly, e.g.:

if (f(p,t) < c) take action A1 else take action A2
Example: c = 1.0000, N = 3. Outputs are 0.9999, 0.9998 and 1.0001. V1 and V2 are below c (do A1) and V3 is above (does A2), though all three are working correctly.

It can happen however precise the versions are. No general fix exists: any algorithm that maps nearby n-bit integers (differing by less than 2k) to the same output must map every input to the same number, which is useless. It can occur wherever a variable is compared with a threshold.

Why it matters: the system can’t tell whether disagreement means errors or just this problem. Two failed versions with the same wrong answer (common bug) could outvote the correct ones.

Fixes:

  • Agree on a consensus value of x before comparing. Drawbacks: the order of comparisons must be fixed, which reduces diversity (more correlated errors), and fast versions wait for slow ones.
  • Confidence signals: if |x − c| < δ (a preset small number), a version announces low confidence; the voter ignores it or gives it less weight. Drawback: other correct versions are probably also near c and are also devalued, so a wrong result far from c might outvote several correct ones.

How often the problem appears depends on the application. If calculations use only the latest inputs (no memory of past values), it is rare and quickly goes away.

Problem 2: version independence

Correlated (related) errors can raise error probability by orders of magnitude.

Example: N = 3 tolerates one bad version. Each version outputs a wrong answer with q = 10−4 (once in 10,000 runs). If independent, the system fails with probability q³ + 3q²(1−q) ≈ 3 × 10−8. Now suppose one shared bug in all three versions is triggered once per million runs. Then the system fails with probability over 10−6, more than 30 times worse.

The input space has regions with different failure chances (e.g. a numerically unstable region fails more). Using the total probability formula, with Si = region i:

P(Vj fails) = Σ P(Vj fails | Si) · P(input in Si)
P(V1 and V2 both fail) = Σ P(V1 fails | Si) · P(V2 fails | Si) · P(Si)
Example 1 (two regions, each 0.5 likely). Failure probabilities: V1 = 0.010 in S1, 0.001 in S2; V2 = 0.020 in S1, 0.003 in S2.
P(V1 fails) = 0.01×0.5 + 0.001×0.5 = 0.0055; P(V2 fails) = 0.0115. If independent: 0.0055 × 0.0115 = 6.33×10−5. Actual both-fail = 0.01×0.02×0.5 + 0.001×0.003×0.5 = 1.02×10−4, higher, because both are weak in S1 (positively correlated).
Example 2: V1 = 0.010 / 0.001, V2 = 0.003 / 0.020. Both-fail = 0.01×0.003×0.5 + 0.001×0.02×0.5 = 2.5×10−5, about 5× lower than Example 1 and less than half the independent value. Now negatively correlated: V1 is strong where V2 is weak and vice versa, so they cover each other.

Ideally versions are negatively correlated; realistically they are positively correlated since they solve the same problem. Historically, the goal has been to make them as independent as possible.

What ruins independence

  • Common specifications – a spec error is copied into every version.
  • Intrinsic difficulty – some inputs are hard for everyone, so versions fail on the same inputs.
  • Common algorithms – the algorithm itself may be unstable in some region, and all versions inherit it.
  • Cultural factors – similarly trained programmers make similar mistakes and read vague specs the same wrong way.
  • Common platforms – same hardware, OS or compiler; their bugs cause correlated failures (strictly not an application bug, but the user still sees a failure).

How to gain independence

Incidental diversity: a by-product of keeping teams apart. Teams may not talk to each other; questions go to a central authority who corrects the spec and informs all teams; inspectors must not leak information between versions.

Forced diversity: deliberately push teams to differ:

  • Diverse specifications – many bugs (some say two-thirds) come from faulty specs, so let diversity start at the spec stage. Versions can even have different capability, e.g. one simpler, less accurate but acceptable and less error-prone.
  • Diverse programming languages – assembly is more bug-prone than high-level languages; different languages bring different libraries and compilers with uncorrelated bugs.
  • Diverse tools and compilers – “notational diversity”; tools themselves can be faulty.
  • Cognitively diverse teams – people who reason differently.
  • Diverse hardware and OS – each version on a different processor type and OS.

Other issues

  • Back-to-back testing: feed the same input to all versions and compare outputs to find bugs that don’t coincide. You can also compare intermediate variables for better visibility into hidden defects, but forcing every version to produce them reduces diversity.
  • Cost: software is expensive and N versions cost more. One study: each extra version adds 25% to 134% of the single-version cost, plus management overhead.
  • One great version vs many? With a fixed time budget, is it better to polish one version or build N? Reliability modelling is not advanced enough to say.

7. Recovery block – one runs, the others wait as backups

Also uses multiple versions, but only one runs at a time. If it fails, switch to a backup. Pieces: a primary, secondaries (backups) and an acceptance test.

Steps: run the primary → test the output → if OK, accept. If not, roll back (restore the system to how it was before the primary started) and run secondary 1. Repeat through the secondaries. If all fail, the recovery block has failed and the system must take corrective action.

Success depends on: (a) how often versions fail on the same inputs (correlated bugs), (b) the quality of the acceptance test.

Success probability (versions fail independently)

Eoutput of a version is wrong
Ttest reports the output is wrong
f = P(E)failure probability of one version
s = P(T|E)test sensitivity
σ = P(E|T)test specificity
nnumber of versions (primary + secondaries)

The scheme succeeds at stage i if the test rejected stages 1 to i−1 and at stage i the output is correct and passes:

P(success at stage i) = [P(T)]^(i−1) · P(Ē ∩ T̄)
P(T) = s·f/σ, P(Ē ∩ T̄) = (1−f) − (1−σ)·s·f/σ
Total = Σ (i=1..n) [sf/σ]^(i−1) · [(1−f) − (1−σ)sf/σ] = (1 − (sf/σ)ⁿ)/(1 − sf/σ) · [(1−f) − (1−σ)sf/σ] …(1)
What the graph shows (n = 3, s and σ = 0.85 or 0.95): success probability drops as f grows. Sensitivity matters more than specificity: the two s = 0.85 curves are much lower than the s = 0.95 curves, whatever σ is.

Distributed recovery blocks

Two nodes hold identical copies of primary and secondary. Node 1 runs the primary while node 2 runs the secondary at the same time. If node 1 fails its acceptance test (or a watchdog timer expires with no output), node 2’s output is used. Then the roles swap: node 2’s copy becomes the primary and node 1’s the backup, until that one fails, and they swap back.

Advantage: no waiting for rollback and then a secondary run, since execution overlaps. This saves time, ideal for real-time systems with tight deadlines.

8. Preconditions, postconditions and assertions

These are acceptance tests built into code that catch errors before they spread. The programmer decides what corrective action to take.

  • Precondition: must be true when a method is called. Example: a square root method for real numbers needs a non-negative input.
  • Postcondition: must be true when the method returns. Example: a natural log method given X returns Y, so eY = X.
  • Assertion: a generalisation; a condition that must be true at the point where it is written.
Example: the total of node degrees in an undirected graph must be even. Assert that after computing it; if odd, an error occurred, and the usual response is to notify the user or take other action.
Contract idea: the caller promises the preconditions hold. The method promises the postconditions hold. If the caller breaks its promise, no correct result is guaranteed.

9. Exception handling

An exception is a signal that something needing attention happened (e.g. an assertion failed due to a hardware or software fault). Control jumps to an exception handler, a routine that responds. Good handling greatly improves fault tolerance, which is why much real code is exception handling.

Example: y = a × b overflows, so the result is wrong. Signal an exception and react.

Uses of exceptions

  • Domain error: illegal input. sqrt(Y) with Y = −1 for real numbers (fine for complex numbers).
  • Range error: output or operation is wrong: hitting end-of-file too early; result fails an embedded acceptance test; printing a too-long line; arithmetic overflow or underflow.
  • Out-of-the-ordinary event (rare but normal): e.g. the last item of a file was just read, so notify the caller nothing more is available.
  • Timing failure: a deadline is missed; the handler may switch to a backup routine.

What we want from an exception system

  • Easy to use and modular, separate from normal code (mixing makes code hard to read and debug).
  • Little overhead in normal running, since exceptions are rare.
  • Must not leave the system state inconsistent.

Basics

  • An exception is thrown / raised / signalled. Some distinguish raising (notify within the same module) from signalling (notify propagates to another module).
  • Internal exception: handled in the same module. External: propagates elsewhere (e.g. an interface exception when a module is called against its interface rules).

Propagation

A calls B; B hits exception c but has no handler, so it sends it back to A, which handles it. If no handler is found anywhere, execution is terminated.

Exception-terminate (ET) vs exception-resume (ER)

Terminate (ET)Resume (ER)
What happensModule M stops, handler runs, control returns to M’s callerHandler tries to patch the problem and returns control to M, which carries on
DifficultyMuch simplerHarder

With ET, B restores its state to what it was when called, signals, and ends. A only sees two outcomes: B succeeded, or B failed with state unchanged. With ER, A may see: (1) no exception; (2) exception handled and B resumed and finished; (3) handler sent control elsewhere. Then control returns to A.

What to do after handling

  • Domain error: call again with corrected operands; if impossible, abandon the computation.
  • Range error: substitute an acceptable value and resume.
  • Out-of-the-ordinary: programmer decides case by case.
  • Timing failure: for iterative routines, use the latest value, e.g. the best result found so far in an optimum search.

Language support: older languages have little; C++ and Java have extensive support. In Java you can define exceptions for conditions (e.g. reactor temperature over a limit) that must be caught by a handler that raises an alarm or prints output.

10. Software reliability models

Defect/bug: mistake in code, exists from when it is written. Error: the program deviating from its requirements because of a bug; it only occurs while running or testing. Software reliability = probability of error-free operation in a given environment for a given time. This needs the error rate λ (errors per unit time). Models predict the error rate from the number of bugs, to decide how long to test and fix until the predicted error rate falls below a chosen threshold.

Shared assumptions: unknown number of bugs at the start; during testing some bugs cause errors; each error’s bug is fixed instantly without adding new bugs (bug count drops by one). Models differ in how they describe λ(t).

Jelinski–Moranda (JM) model

  • Fixed, finite N(0) bugs at start; N(t) remain at time t.
  • Errors follow a non-homogeneous Poisson process (random events whose rate can change over time).
  • λ(t) = c·N(t) (c constant), so the rate is proportional to remaining bugs. It is a step function: starts at λ₀ = cN(0), drops by c at each fix, constant between errors.
  • Time between errors is exponentially distributed. R(t) = e−λ₀t; after an error at time τ: R(t|τ) = e−λ(τ)t (the chance the next t time units are error-free).
Meaning: the longer you run and fix, the lower the error rate and the higher the reliability. Weakness: it assumes all bugs matter equally (same c). In truth some bugs trigger often, and rarely exercised ones are the hardest to catch in testing.

Littlewood–Verrall (LV) model

  • Also fixed finite N(0) bugs, but uses M(t) = N(0) − N(t), the bugs found and fixed by time t.
  • Errors follow a non-homogeneous Poisson process, but λ(t) is itself a random variable with a Gamma distribution (parameters α and ψ, where ψ increases with M(t)).
  • Expected error rate = α/ψ(M(t)). It falls as more bugs are fixed.
  • R(t) = (1 + t/ψ(0))−α; R(t|τ) = (1 + t/ψ(M(τ)))−α.

Musa–Okumoto (MO) model

  • Assumes an infinite or very large number of bugs. λ₀ = initial error rate, c = constant, μ(t) = expected errors in [0, t].
  • λ(t) = λ₀ e−cμ(t). Idea: easy bugs go first; the rest are harder to trigger or hidden, so the rate for an undiscovered bug drops exponentially.
  • Solving dμ/dt = λ₀e−cμ gives μ(t) = ln(λ₀ct + 1)/c and λ(t) = λ₀/(λ₀ct + 1).
  • R(t) = (1 + λ₀ct)−1/c; R(t|τ) = (1 + λ₀ct/(1 + λ₀cτ))−1/c.
Graph takeaway: the error rate falls very slowly, so getting it low enough takes a lot of testing.

11. Fault-tolerant Remote Procedure Calls (RPC)

An RPC lets one process call a procedure running on another processor. It is widely used in distributed computing.

Primary–backup approach

Each process has a primary and a backup on separate nodes. Calls go to both, but normally only the primary runs them; if it fails, the backup takes over and finishes.

  • Retryable RPC: safe to run many times, e.g. reading a database. Easy to support.
  • Non-retryable RPC: must run exactly once, e.g. adding to a bank balance. The primary checkpoints (saves its progress) on the backup so the work is not repeated.

The circus approach

Client and server processes are each replicated; a replica set is a troupe (circus metaphor). Four client copies make identical calls to four server copies.

  • Every call has a unique sequence number; replies too.
  • A server waits for identical calls from all client copies (or a timeout), then runs the RPC and sends results to every client.
  • A client may wait for identical replies from all servers (with a timeout so it doesn’t wait forever for a dead server), or just take the first reply.

Extra complication: order of calls

If several client troupes call the same server troupe at once, every server must handle calls in the same order. Two ways:

  • Optimistic: let everything run, then check whether order was kept. If yes accept; if not, abort and retry. Very slow if order is often broken.
  • Pessimistic: built-in steps keep the order. A server that is ready sends ready_to_commit to every member of the client troupe and waits for all acknowledgments before committing. A client waits for ready_to_commit from every server before acknowledging. Only after all acknowledgments does the server commit.
Why it works (example): clients C1, C2 send calls ρ1, ρ2 to servers S1, S2. S1 wants to commit ρ1 first; S2 wants ρ2 first. C1 members wait to hear from both S1 and S2 but never hear from S2; C2 members never hear from S1. Result: deadlock (everyone waits on everyone). Deadlock-detection algorithms notice it, the operations are aborted before commit and retried. So wrong ordering is turned into a detectable deadlock.

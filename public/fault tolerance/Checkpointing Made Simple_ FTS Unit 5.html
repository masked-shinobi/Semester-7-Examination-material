PART 1

Why do we need checkpointing?

Some programs run for days even on the fastest computers: weather and climate simulation (fluid flow), airline crew and aircraft scheduling (optimization), planets and stars pulling on each other (astronomy N-body), and protein folding for personalised medicine (biochemistry). The longer a program runs, the more likely a failure hits it, and the more work a failure destroys.

ExampleTyping a 50-page essay without ever saving. One power cut and all 50 pages are gone. Checkpointing is the “Save” button for programs.

The maths in plain words

  • T = time the program needs if nothing goes wrong.
  • λ (lambda) = how many failures happen per unit time. We assume transient point failures: they cause an error, vanish, and all work done so far is lost; recovery takes no time.
  • E = expected (average) actual running time, counting wasted work.

Two cases: (i) no failure, chance e−λT, time is T; (ii) at least one failure, say at time τ, so you lose τ and must start over, costing τ + E more. Adding both cases and solving gives:

E = (e^(λT) − 1) / λ

E grows exponentially with T: double the program length and the average time can far more than double. The penalty is measured by η = (E − T)/T = (e^(λT) − 1)/(λT) − 1, “extra time as a fraction of T”. It depends only on λT = expected number of failures during the run.

Fig. η versus λT (from slide 8: η ≈ 5 when λT = 3)
Key ideaLong program + failures = exponential waste. Fix: save progress regularly so a failure only costs the work since the last save.
PART 2

What is checkpointing?

Example (calculator)You add a long list of numbers and write the partial sum on paper after every 5 additions. You press Clear by mistake after 7 numbers. Instead of redoing 7 additions you take the sum written after 5 and add only the 6th and 7th. Those written sums are checkpoints.
CheckpointA snapshot of the entire state of a process at one moment: everything needed to restart from that point.
Stable storageStorage you trust to survive failures. Usually disks: they keep data when power is cut and are cheap for huge amounts.

Overhead vs latency (often confused)

TermMeaning
Checkpoint overheadHow much taking a checkpoint slows the application (time the program is paused).
Checkpoint latencyTotal time to finish saving the checkpoint.

In a very simple system they are equal. If the CPU copies state to a buffer and then carries on while another unit writes the buffer to disk, the pause (overhead) is short but the whole save (latency) is longer. The checkpoint is only usable once it reaches the disk.

Size matters. Latency depends on checkpoint size, which changes as a program runs. In the slide’s C code, the first loop only keeps a minimum value (small state); the second multiplies a matrix (big state), so a checkpoint taken there is larger.

Why is it not trivial? Five questions to settle

  1. At what level (user or kernel) do we checkpoint, and how transparent is it to the user?
  2. How many checkpoints?
  3. At which points in the program?
  4. How do we reduce overhead?
  5. How do we checkpoint distributed systems with passing messages, with or without a central controller?
PART 3

Checkpoint levels: who does the saving?

LevelWho does itGoodBad
KernelThe operating system core manages checkpoints and recovery.Transparent; programs need no changes.Needs OS support.
UserA library; programs are linked to it. Library also manages recovery.No code changes, only linking.Cannot see kernel information.
ApplicationThe programmer writes checkpoint and recovery code inside the program.Most control.Costly to write and debug.
Limits of user/application level
  • The kernel does not see threads, and user levels cannot see kernel data.
  • They cannot demand a particular process ID on recovery, so one program may get different process IDs over its life.
  • They may not be allowed to save parts of the file system, so they store file names and pointers instead.
PART 4

Optimal checkpointing: how many, and how far apart?

Too few checkpoints: a failure loses lots of work. Too many: you waste time saving. We want the sweet spot.

Symbols

SymbolMeaning
TltLatency: start to end of one checkpoint (t2 − t0).
TovOverhead: the part when the app is blocked (t1 − t0).
TrAverage recovery time after a failure.
NNumber of checkpoints, spread evenly.
TexUseful work between checkpoints = T/(N+1).
EintAverage time between two completed checkpoints.

If a failure strikes during a checkpoint’s latency, that checkpoint is useless and we go back to the previous one. If no failure, Eint = Tex + Tov. If a failure comes τ later, we lose τ + Tlt − Tov of work and also need Tr to recover.

First-order approximation (at most one failure per interval)

  • Case 1 (no failure): probability e−λ(Tex+Tov), contributes (Tex+Tov) times that.
  • Case 2 (one failure): probability 1 − e−λ(Tex+Tov); average τ = (Tex+Tov)/2; extra time = τ + Tlt − Tov + Tr.

Add them to get Eint. Take derivatives: dE/dTov ≈ ½ + […]e^(−λ(Tex+Tov)) but dE/dTlt ≈ 1 − e^(−λ(Tex+Tov)).

Big lessonEint is far more sensitive to overhead Tov than to latency Tlt. So keep overhead low, even if that makes latency much longer.

The checkpoint placement problem

Choose N (or Tex) to minimise the total run time, i.e. the figure of merit η = Eint/Tex − 1. Differentiate and set to zero:

Tex_opt = √( 2·Tov/λ + 2·Tov·(Tr + Tlt − Tov/2) ) and N_opt = T / Tex_opt − 1

More accurate model: allow more than one failure per interval. After a failure the process resumes and needs another Eint on average. The result is Eint = (Tr + Tlt − Tov + 1/λ)(e^(λ(Tex+Tov)) − 1). The best Tex satisfies e^(λ(Tex+Tov)) = 1/(1 − λ·Tex), and again Nopt = T/Tex_opt − 1. Overhead still matters more than latency.

PART 5

Making checkpoints cheaper

Reduce overhead

  • Buffering: write the checkpoint to a part of main memory and continue. DMA (direct memory access) copies it to disk and needs the CPU only at start and end.
  • Copy-on-write: do not copy unchanged pages again. At checkpoint time mark all pages read-only (memory protection bits: read-write, read-only, inaccessible). The app keeps running. If it tries to change a page, an access violation fires; the system buffers that page, makes it read-write, and copies it to disk later. Fewer updates mean less copying.
  • Incremental checkpointing: save only the changes since the previous checkpoint (copy-on-write is an example).
  • Memory exclusion: do not save data you do not need: variables not updated since last time, and dead variables (value never used again).
Dead variable examples(a) a variable the program never reads again, (b) a variable whose next access is a write, so the old value is overwritten before being read.

Reduce latency

Checkpoint compression: smaller checkpoint, less to write. How much it helps depends on how well the data compresses (sometimes over 50%, sometimes barely) and on CPU time to compress (which adds to overhead). In simple sequential checkpointing, where the CPU waits for the disk, compression pays off when disk time saved is greater than compression time.

PART 6

Checkpointing in distributed systems

A distributed system is many processors, each with memory (and maybe local disks), joined by a network. Think of it as processes joined by one-way channels (point-to-point links, error-free, delivering messages in order). The state of a channel = the messages it carried so far. The state of the system = states of all processes + all channels.

Consistent state, orphans, recovery line

Consistent stateEvery message recorded as received is also recorded as sent. (Sent but not yet received is fine.)
Orphan messageRecorded as received but never recorded as sent: an effect with no cause, which breaks causality.
Fig. 1: P sends m to Q after CP1; Q receives it before CQ2
  • {CP1,CQ1}: neither knows m. Consistent.
  • {CP2,CQ1}: sent, not received. Consistent.
  • {CP2,CQ2}: sent and received. Consistent.
  • {CP1,CQ2}: CQ2 says “received m” but CP1 says “never sent m”. Orphan, inconsistent.
Recovery lineA set of checkpoints that forms a consistent state. We can roll the whole system back to it. E.g. rolling back to {CP1,CQ1} makes P resend m. For {CP2,CQ1}, Q has lost m, so it must be replayed from a message log (or P’s checkpoint).

Useless checkpoint: one that can never be in a recovery line. In Fig. 2, CQ2 records receiving m1 but not sending m2, so pairing it with CP1 or CP2 always creates an orphan.

Domino effect

Domino effectWith uncoordinated checkpoints, one failure forces a chain of rollbacks that pushes every process all the way back to the start, like falling dominoes.

Slide example: P fails, rolls back to CP3. It sent m6 after CP3, so Q must go back before receiving m6 (else orphan), i.e. to CQ2. But Q sent m5 to P, so P must roll back to CP2, and so on, until all return to the start. Cause: insisting on no orphans while checkpoints are uncoordinated.

Lost messages and livelock

  • Lost message: Q rolls back to before it received m, but P does not roll back to before sending it. m is lost. Milder than an orphan (no causality violation); it can be resent. But an acknowledgment Q already sent would become an orphan unless P rolls back too.
  • Livelock: processes keep rolling back and repeating forever. Slide example: Q sends m1 to P, P sends m2 to Q, P fails before receiving m1. Q rolls back so m2 is not orphaned; P recovers and resends m2, then receives the old m1, which is now an orphan because Q rolled back, which orphans the new m2, forcing Q to roll back again... it never ends without outside intervention.

Fix 1: Coordinated checkpointing

If P takes checkpoint CP3 that records “received m from Q”, then Q must also checkpoint to record “sent m”. Two kinds of checkpoint:

  • Tentative: P saves state, then tells every process it received a message from (set P̂) the last message mqp it got from each.
  • If Q has not recorded sending mqp, Q takes a tentative checkpoint too.
  • If all confirm, tentative become permanent. If any cannot, all abandon theirs.
  • Can cause a chain reaction: each member of P̂ may force others.

Fix 2: Time-based synchronization

If everyone checkpoints at exactly the same instant, no orphans. Impossible in practice (clock skew, message delay), but we can agree to checkpoint when each local clock reads, say, a multiple of 100 s. Alone this fails: P0’s clock may run ahead, so it checkpoints earlier in real time, sends a message, and P1 receives it before its own checkpoint (Fig. 7: orphan).

  • Let maximum clock skew be δ. After checkpointing at local time τ, P0 stays silent during [τ, τ+δ].
  • If a minimum message delay ε is known, silence only needs [τ, τ+δ−ε] (if ε > δ, no silence at all).
  • Alternative: the receiver ignores (does not use or include in its checkpoint) messages arriving in [τ−δ+ε, τ] until it has taken its own checkpoint at τ.

Algorithm with two phases (n processes P0 … Pn−1)

  1. Checkpointing phase: P0 checkpoints and orders P1 to; P1 checkpoints and orders P2; … Pn−1 orders P0. This closes the loop.
  2. Message-logging phase: P0 sends marker messages on all outgoing channels. A process getting its first marker in this round forwards markers and logs all messages received after its checkpoint and before the marker; later markers just add newly received messages to the log.

Staggered checkpointing

If all processes checkpoint at nearly the same time to shared storage, disks and network jam. Remedies: (1) write to a local buffer first, then spread the writes; (2) take checkpoints one at a time, and then have a logging phase where each process stores the messages it sent since its last checkpoint. Messages are smaller than checkpoints, so the surge is small. A process can be recovered up to time τ (first message not logged). Checkpoint + message log = logical checkpoint, and all logical checkpoints form a consistent recovery line.

Fig. 9 walk-throughP0, P1, P2. P0 (coordinator) checkpoints and sends take_checkpoint to P1, which checkpoints and tells P2, which tells P0. Phase 2: P0 sends message_log orders to P1 and P2. P1 logs its messages; P2 has none. P0 later logs m5. Each process recovers up to the moment it gets a message that is not logged.

Diskless checkpointing

Main memory loses data on power loss, but with extra processors we can borrow RAID ideas and skip the disk (much faster). Best as one level of a two-level scheme.

Six executing + one extra processor holding the parity of all checkpoints. If one fails, rebuild its checkpoint from the other five + parity. (Parity = a combined check value, like a total that lets you find one missing number.) RAID-1 analogue: keep two copies of every checkpoint (mirroring), surviving one failure. Hotspot: if everyone sends checkpoints to one processor, it becomes a traffic jam; fix by distributing parity computation in a tree (Fig. 8). Network bandwidth must be large enough.

Message logging (uncoordinated checkpoints)

To recover, roll back to the last checkpoint, then replay all messages received since, in the original order. With coordinated checkpoints messages are resent automatically; with independent checkpoints we log messages to stable storage.

PessimisticOptimistic
HowReceiver stops, logs each message to stable storage, then continues.Messages go to fast volatile buffer, copied to stable storage later.
RecoveryVery simple; no other process rolls back; no orphans.Complex; buffer may be lost, so several processes may roll back; need a recovery line computation.
CostHigh overhead (stable writes).Very low overhead.

Sender-based logging (for at most one failure at a time)

  • The sender keeps the log in a fast buffer.
  • Each process has a send-counter and receive-counter. A message carries an SSN (Send Sequence Number). The receiver gives it an RSN (Receive Sequence Number) and acknowledges with the RSN; the sender acknowledges that acknowledgment.
  • Until that last acknowledgment, the receiver must not send messages to others (vital for correct recovery).
  • Fully logged: sender knows SSN and RSN. Partially logged: RSN unknown (receiver failed before or after receiving, before acknowledging).
  • On recovery, a process tells the others the SSN of the last message it recorded; they resend later ones. Partially logged ones may arrive in a different order, harmlessly, since the receiver sent nothing meanwhile.
PART 7

Checkpointing in shared-memory systems

Setting: several processors on a bus, each with a private cache (small fast memory). Cache coherence keeps all copies of the same data in agreement. We add checkpointing by tweaking this protocol.

Cache line states (original)

  • Invalid: not usable. Shared unmodified: copy may exist in other caches. Exclusive unmodified: only valid copy, same as memory. Exclusive modified: only valid copy, changed since it left memory.
  • Shared → write → exclusive modified. A write miss = read miss + write hit → exclusive modified. If another cache issues a read on the bus, the holder supplies the data, updates memory, and goes to shared unmodified.
Red box = new state added for checkpointing (Fig. 11)

With checkpointing: the exclusive-modified state splits into exclusive modified and unmodifiable. Once a line becomes part of a checkpoint it is unmodifiable; before it can change it must first be copied to memory, so the checkpoint copy is kept for rollback.

Counter version: each cache line has a multi-bit checkpoint id Cid and there is a counter Ccount. Taking a checkpoint = increment Ccount. Updating a line sets Cid = Ccount. A modified line with Cid < Ccount belongs to the checkpoint, so it is unmodifiable; writes wait until it is written to main memory. With k bits the counter wraps after 2k−1; at that point all modified lines get Cid reset to 0.

Directory-based protocol

A central directory (run by a shared-memory controller) records each line’s status and handles all misses. A cache that wants to modify a line tells the controller, which changes the state. Checkpointing is easy to add on top of this.

PART 8

Checkpointing in real-time systems

A real-time system must meet deadlines. Hard real-time: missing one is very costly (process control, remote vehicle control). Soft: missing lowers quality but is not a disaster (watching a movie online). The application decides which it is.

Different goalHere we do not minimise average run time. We maximise the probability of meeting all critical deadlines. Checkpointing may even raise average time; that price is worth paying if the chance of a missed deadline falls enough.

The model in words

  • Checkpoint after every Tex of useful work; each costs Tov (latency = overhead here). Faults at rate λ; recovery takes Tr.
  • We use the density function f(t) (how likely each possible run time is), not just the average.
  • Interval time is exactly Tex+Tov if no failure (Case 1); more if there is at least one (Case 2). It can never be less than Tex+Tov, nor fall in (Tex+Tov, Tex+Tov+Tr).
  • With N checkpoints, total time density = (N+1)-fold convolution of the interval density. Probability of missing deadline td: pmiss = ∫ from td to ∞ of fexec(t) dt.

  • Tight deadline (little slack): more checkpoints hurt. Example: deadline 0.3, three checkpoints beat six.
  • Loose deadline (more slack): more checkpoints help. Example: deadline 0.5 with Tov=0.015, six beat three.
PART 9

Real machines that use these ideas

IBM G5 processor

Aimed at transient faults (the most common). I/O: physical replication and multiple paths that can be switched around faults, plus inline error checking. Memory: error-correcting codes.

  • I-unit (fetch, decode, queue instructions) and E-unit (execute, update state) are duplicated and run in lock-step. Matching results = fine; mismatch = error.
  • R-unit: 128 32-bit and 128 64-bit registers, ECC-protected, storing the checkpointed state. It is updated only when both E-units agree.
  • ECC-protected store buffer; L1 writes go through to L2, so a backup always exists. L1 errors are found by parity and fixed from L2; L2, memory and buses use ECC. Address bus: 1 parity bit per 24 bits.
  • Bad L2 line: invalidated; if dirty and correctable, the fixed line goes to main memory. Same failure repeating in one spot = permanent fault; that line is retired.
  • Memory scrubbing: regularly read all memory and correct bit errors before they pile up beyond ECC’s power.
  • Recovery: on a mismatch, retry: freeze R-unit, finish pending write-throughs, reload registers from R-unit, restart. If it keeps failing (permanent fault), move the checkpoint to a spare processor. Usually invisible to the OS and applications.

IBM Sysplex

  • Up to 32 nodes, a global timer (common time to order events), and a storage director linking all to shared disks through redundant connections.
  • Shared disk lets a task restart on another node. The Automatic Restart Manager (ARM) does this, knows each node’s load (load balancing), task affinity groups (tasks that must stay on the same node), ordering rules (restart P only after Q), maximum restart attempts and memory needs.
  • Danger: two copies of the same task alive (e.g. wrong database updates). So make sure the failed node is truly down, and forbid restarts on nodes that lost access to the global state.
  • How: SysSeqNum(x) goes up each time node x loses and regains access. A process registers with the current value; if it later differs, the process is de-registered from recovery.
  • Hot-standby: primary and secondary servers; if the primary fails, use the secondary’s output, a much faster switch.

Intel Itanium

64-bit server chip, EPIC (compiler bundles up to 6 instructions per cycle, avoiding data dependencies). Built for availability.

  • Parity and ECC on data buses and three cache levels (L1I, L1D separate; L2, L3 unified). L1: parity; on error the whole cache is invalidated. L1D has byte-wise parity. Bits of neighbouring lines are interleaved because faults hit nearby locations together, so a multi-bit error is less likely in one line. L2 data: ECC, tag: parity (1 bit per ≤24 bits). L3: ECC on both. Single-bit errors corrected silently; a tag error scrubs all four ways.
  • If corrected: a “corrected machine check” interrupt and carry on. If not correctable but must be contained: bus reset (clears pending transactions, keeps architectural state). Otherwise a Machine Check Abort (MCA): local (only that processor/thread knows) or global (all processors told).
  • Handled layer by layer: hardware, then PAL (hides the processor), then SAL (hides the rest of the system), then the OS (e.g. kill the guilty process). Worst case: local or full reboot and I/O re-initialisation.
  • Data poisoning (at L2): mark bad data instead of rebooting. Stores to a poisoned line are ignored; if evicted it is written to memory with a poison flag; any process fetching it triggers an MCA and only that process is aborted.
  • Error info goes to the OS by interrupt or polling. The OS can, for example, stop using a memory page with a high error rate. Itanium is used in fault-tolerant machines such as the newest NonStop systems.

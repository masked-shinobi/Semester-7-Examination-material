1 · What is Fault Tolerance?

DefinitionFault tolerance is the ability of a system to keep working correctly even when some of its parts fail. The system notices the problem, isolates it, and continues giving service.

Why do we need it? Some systems cannot afford to stop: banking, air traffic control, medical equipment, nuclear plants, spacecraft, cloud computing, military. A failure there can mean lost money, lost data, stopped service, or even danger to human life.

Example – aeroplaneIt has 2 engines, 2 navigation systems and a backup radio. If one engine dies, the plane still flies on the other. That is fault tolerance.
Example – ATMNetwork cable gets disconnected → ATM detects it → switches to backup network → your transaction continues.

2 · Fault, Error and Failure

Students mix these up. They are three different stages of one problem.

FAULTthe cause (something is broken)
→ produces →
ERRORwrong state inside the system
→ leads to →
FAILUREuser sees wrong output
Fault
A physical defect, flaw or mistake in hardware, software, network or human operation. It is the root cause. It may sit hidden and cause nothing yet. Ex: short circuit, broken pin, software bug.
Error
A wrong value or wrong condition inside the system caused by a fault. Users usually cannot see it. If it is corrected in time, it never becomes a failure.
Failure
The service given to the user is wrong or stops, i.e. it deviates from the system specification. Visible to users. Every failure is caused by one or more errors.
Example 1 – KeyboardFault: a damaged key → Error: pressing “A” sends “S” to the computer → Failure: the assignment has wrong words and cannot be submitted.
Example 2 – Bank transfer of ₹10,000Fault: bug in the banking app → Error: database stores ₹1,000 → Failure: receiver gets only ₹1,000.
Example 3 – Damaged RAMFault: RAM chip defective → Error: wrong data saved in memory → Failure: system crash or wrong result.
From the slides – stuck adderAn adder circuit has an output line stuck at 1 (fault). It causes an error only when that line should have been 0. If the correct answer was 1 anyway, nothing goes wrong.
From the slides – sin(x) bugA subroutine should compute sin(x) but, by a programming mistake, computes |sin(x)|. This causes an error only when the subroutine is used and the correct answer is negative. So a fault does not always produce an error.

3 · Fault Classification

DefinitionFault classification means grouping faults by their duration, origin, behaviour and location (Israel Koren). It helps engineers pick the right detection and recovery method, reduce downtime and design better systems.

A. By duration

Permanent
Stays until the part is repaired or replaced. Never disappears alone. Easy to detect. Causes: burnt motherboard, damaged hard disk, failed CPU, broken power supply. Ex: hard disk physically damaged – restart does not help; a burned-out light bulb.
Transient
Appears for a short time, then vanishes without repair; component works fully again. Hard to reproduce. Causes: power fluctuation, electromagnetic interference, cosmic radiation, voltage spikes, network congestion. Ex: PC restarts due to a power dip; noise during a phone call.
Intermittent
Comes and goes repeatedly at irregular times; never fully goes away (flips between inactive and active). Very hard to diagnose. Causes: loose cable or RAM, overheating, weak solder joints. Ex: monitor goes blank now and then due to a loose cable.

Memory trickPermanent = replace it. Transient = wait, it goes. Intermittent = comes and goes.

B. Benign vs Malicious (by behaviour)

Benign
The unit just goes dead. Easiest to handle because everyone can see it stopped.
Malicious
The unit gives reasonable-looking but wrong output, or even sends different values to different receivers. Much more dangerous. Ex: an aircraft altitude sensor tells one unit “1000 ft” and another unit “8000 ft”.

C. By origin

Hardware
Physical part fails: CPU failure, RAM damage, disk crash, power supply failure.
Software
Design or coding mistake: bug, infinite loop, buffer overflow, wrong algorithm.
Human
Mistake in operation/maintenance: deleting files by accident, wrong password, wrong configuration.
Network
Communication problem: router/switch failure, broken fibre cable, packet loss from congestion.

4.1 Traditional measures

Failure rate (λ, “lambda”)Average number of failures per unit of operating time. Low is good.
λ = Number of failures ÷ Operating time
ExampleServer runs 1000 hours, fails 5 times → λ = 5/1000 = 0.005 failures/hour.
MTTF – Mean Time To FailureAverage time a system works before it fails (used for parts that are replaced, not repaired). High is good.
MTTF = Total operating time ÷ Number of failures
Example: 1000 h, 5 failures → 200 hours.
MTTR – Mean Time To RepairAverage time needed to repair a failed system. Low is good.
MTTR = Total repair time ÷ Number of repairs
Example: 10 h repair in total over 5 repairs → 2 hours.
MTBF – Mean Time Between FailuresAverage time between two consecutive failures. It includes working time and repair time. High is good.
MTBF = MTTF + MTTR
Example: 200 + 2 = 202 hours.
Reliability R(t)Probability that the system works continuously, without any failure, during the time interval [0, t]. Value from 0 to 1. Important where even a momentary break is costly, e.g. aircraft control computers.
AvailabilityThe fraction of time the system is up and ready to serve. Important where short downtime is tolerable but long downtime is costly, e.g. an airline reservation system.
Availability = MTTF ÷ (MTTF + MTTR) = MTTF ÷ MTBF
Example: MTTF 99 h, MTTR 1 h → 99/100 = 0.99 = 99%.
Point availabilityProbability that the system is up at one particular instant t.
Low reliability but high availability?Yes! A system fails every hour (MTBF = 1 h → low reliability) but comes back in just 1 second. Availability = 3599/3600 = 0.99972. It fails often, but is almost always up.

4.2 Network measures

These look at the network connecting the processors, focusing on data transfer instead of single machines.

Node & line connectivity
Minimum number of nodes (or lines) that must fail before the network splits into disconnected parts. Gives a rough idea of vulnerability. Limit: only knows two states – connected / disconnected – and says nothing about how the network degrades.
Packet loss
% of sent packets that never arrive. Packet loss = lost ÷ sent × 100. Ex: 20 of 1000 lost → 2%. Lower is better.
Latency
Time a packet takes from source to destination. Ex: 30 ms. Lower is better.
Throughput
Useful data actually delivered per second. Ex: 500 MB in 50 s = 10 MB/s. Higher is better.
Bandwidth
Maximum capacity of the channel. Ex: a 100 Mbps line. Bandwidth = maximum speed; throughput = real speed achieved.
Network availability
% of time the network is working and reachable. Higher is better.

5 · Dependable System

DefinitionA dependable system gives correct, safe and continuous service that users can justifiably trust, even when faults occur. Dependability = the ability to deliver its intended level of service to users. The ultimate goal of fault tolerance is a dependable system.

Dependability has three parts (from the slides): Attributes (what we want), Impairments (what harms it), Means (how we achieve it).

Attributes

Reliability
Continuous correct service without failure. Ex: online banking server runs a month without interruption.
Availability
Ready to serve whenever needed. Ex: Google Search – failed servers are instantly replaced by backups.
Safety
No injury, loss of life or environmental damage even when faults occur. Ex: flight control switches to a backup processor.
Integrity
Data is protected from unauthorised change, corruption or loss. Ex: nobody can edit account balances illegally.
Maintainability
Can be repaired quickly and easily. Ex: swapping a faulty server part in minutes.
Fail-safe vs fail-unsafe (safety)For reliability all failures are equal. For safety they are split in two. Take an alarm system: if it fails to ring when danger exists → fail-unsafe (dangerous). If it rings when there is no danger → fail-safe (harmless false alarm).
S(t) = P(works correctly OR stops in a fail-safe way during [0,t])
Power-plant exampleSensor for turbine speed fails → system sends too much steam → turbine over-speeds → mechanical safety system shuts the turbine down. Damage prevented, but power generation stops. This is a fail-safe failure.

Impairments (recap)

Fault → Error → Failure, exactly as in section 2. Faults cause errors, errors cause failures.

Features, importance, advantages, limits

A dependable system…
  • gives correct service
  • detects faults quickly
  • keeps running during failures
  • recovers automatically
  • protects data
  • minimises downtime
  • is easy to repair
Advantages
  • High reliability & availability
  • Better safety & data protection
  • Quick recovery
  • Lower maintenance cost
  • Happy customers, more trust
Limitations
  • Higher development cost
  • More complex design
  • Extra hardware/software redundancy
  • More testing and maintenance
ATM as a dependable systemWorks 24×7. If one server fails, a backup takes over at once, account data stays correct, cash transactions continue, and the failed server is repaired later. → Reliability (correct transactions), Availability (always accessible), Integrity (data protected), Maintainability (quick repair), Safety (no unsafe transactions).

6 · Four Techniques (Means) to Achieve Dependability

1. Fault Prevention
Stop faults from entering the system in the first place. Methods: good design, quality hardware, coding standards, training, documentation, design reviews. Ex: aircraft maker uses certified processors and strict coding rules. Limit: not all faults can be prevented.
2. Fault Removal
Reduce faults that already exist, before or after deployment. Methods: testing, debugging, code inspection, verification, validation, corrective maintenance. Ex: bug found in testing is fixed before release. Limit: hidden faults may remain.
3. Fault Forecasting
Estimate how many faults exist, how many may occur in future, and their consequences. Methods: reliability analysis, failure-rate estimation, simulation, statistical models, risk assessment. Ex: cloud provider predicts disk failures and adds backup storage. Limit: only probabilities.
4. Fault Tolerance
Keep working correctly even when faults occur. Done using redundancy (extra resources). Limit: higher cost and design complexity.

Types of redundancy (how fault tolerance is achieved)

Hardware
Duplicate/triplicate parts. Ex: dual power supplies.
Software
Several versions do the same job. Ex: N-version programming.
Information
Extra bits added to detect or correct errors.
Time
Repeat the operation to beat temporary faults. Ex: resend a lost packet.

What redundancy lets the system do

Maskingonly correct values reach the output
Detectionfind that a fault occurred
Locationfind where it is
Containmentstop it spreading
Recoveryreconfigure around it
  • Fault masking – hide the fault so the output stays correct (like a spare tyre you never notice).
  • Fault detection – two ways: acceptance tests (when nothing is duplicated, check whether the result looks acceptable) and comparison (when parts are duplicated, compare their outputs; a mismatch means a fault).
  • Fault location – decide where the fault happened.
  • Fault containment – isolate the fault so its effect does not spread through the system.
  • Recovery – once the faulty part is identified, the system reconfigures itself to cut it off and returns to working state.

7 · Dependability Measures (with formulas)

Common measures: failure rate, MTTF, MTTR, MTBF, fault coverage. Also: reliability, availability, safety, integrity, maintainability.

Failure rate and the bathtub curve

Failure rate z(t)Expected number of failures per unit time. In hardware it follows a bathtub curve with 3 phases.

I Infant mortality – weak parts fail early, rate drops. II Useful life – low, steady rate. III Wear-out – parts age, rate climbs.

Exponential failure law

During useful life (constant λ), reliability falls exponentially with time:

R(t) = e^(−λt)
Exampleλ = 0.002/hour, t = 100 h → R = e^(−0.2) = 0.8187 → 81.87% chance of no failure.

Failure rate of a system without redundancy

λ = λ₁ + λ₂ + … + λₙ (add every component’s failure rate)
Worked example (slides)Circuit: 16 NAND gates (λ = 0.311×10⁻⁷/h each) + 3 flip-flops (0.412×10⁻⁷/h each). Failures independent.
(1) λ = 16×0.311×10⁻⁷ + 3×0.412×10⁻⁷ = 0.6212×10⁻⁶ per hour.
(2) One year = 8760 h → R = e^(−0.6212×10⁻⁶ × 8760) = 0.9946 (≈ 99.46%).

Software failure rate

In software, failure rate usually decreases over time: I test/debug phase, II useful life, III obsolescence. Small bumps in phase II appear when feature upgrades add new bugs. The exponential law is mainly for hardware. Time-varying rates use the Weibull distribution:

z(t) = αλ(λt)^(α−1)
  • α = 1 → z(t) = λ (constant)
  • α > 1 → rate increases with time
  • α < 1 → rate decreases with time

MTTF in detail

  • MTTF = expected time to the first failure.
  • Test n identical parts, note each one’s time to fail tᵢ: MTTF = (1/n) Σ tᵢ.
  • Link to reliability: MTTF = ∫ R(t) dt (0 to ∞) = 1/λ.
FIT – Failures In TimeNumber of failures expected in one billion (10⁹) hours.
FIT = 10⁹ ÷ MTTF
ExampleMotor, λ = 0.549×10⁻³/h. MTTF = 1/λ = 1822 hours. FIT = 10⁹/1822 = 548,847.

MTTR, repair rate and steady-state availability

Repair rate μ (mu) = expected repairs per unit time.

MTTR = 1/μ MTBF = MTTF + MTTR
A(∞) = MTTF/(MTTF+MTTR) = μ/(μ+λ)
ExamplesMTTF 1000 h, MTTR 10 h → A = 1000/1010 = 0.9901 (99.01%). Five repairs taking 25 h → MTTR = 5 h; with MTTF = 1000 h, MTBF = 1005 h. 5000 h with 5 failures → MTTF = 1000 h.

Fault coverage

Coverage = conditional probability: “given that a fault exists, what is the chance the system handles it?” Four kinds:

Detection coverage
P(system detects the fault)
Location coverage
P(system locates it)
Containment coverage
P(system contains it)
Recovery coverage
P(system recovers)

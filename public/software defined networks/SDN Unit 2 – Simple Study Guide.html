Read once, top to bottom. Every hard word is explained in plain language, followed by an everyday example. Five topics, five colours.

The big idea in one line: In normal networks every switch thinks for itself. In SDN the switches become “dumb but fast workers” and one smart controller (the brain) tells them what to do.
Old network = every traffic policeman at every junction decides alone. SDN = one control room watches the whole city and sends instructions to all policemen.
Words you’ll see everywhere
  • Switch – a device that moves data packets from one place to another.
  • Packet – a small piece of data (like one envelope in the post).
  • Flow – a stream of packets between the same two things (one video call = one flow).
  • Controller – the software brain of SDN.
  • Southbound = controller ↔ switches (down). Northbound = controller ↔ apps (up). East–west = controller ↔ other controllers (sideways).

Topic I – How SDN Works & the OpenFlow Protocol

1. Working principle

Every SDN switch has a flow table – a list of rules saying “if a packet looks like this, do that”. The controller writes the rules. Switches just follow them, very fast, in hardware.

sequenceDiagram
participant A as Host A
participant S as Switch (flow table)
participant C as Controller
participant B as Host B
A->>S: 1 First packet arrives
S->>S: 2 Look up table - no match (table miss)
S->>C: 3 Packet-In (what do I do?)
C->>S: 4 Flow-Mod (new rule)
C->>S: 5 Packet-Out (release the packet)
S->>B: 6 Forward
A->>S: Later packets match the rule
S->>B: Forwarded directly, controller not asked
  1. A packet arrives at a switch port.
  2. Switch compares its header fields with table rules, highest priority first.
  3. Match found → do the rule’s actions and update counters (fast, in the switch).
  4. No match = table miss → switch sends the packet (or its header) to the controller as Packet-In.
  5. Controller decides using its global view, sends Flow-Mod (install rule) and Packet-Out (release the waiting packet).
  6. Next packets of this flow match the new rule and never bother the controller.
A new employee (packet) reaches a company gate. The guard (switch) has no instruction for him, so he phones the manager (controller). The manager says “let him in, and let all his colleagues in too” (Flow-Mod). From then on the guard doesn’t phone again.

Reactive, proactive, hybrid

ReactiveRule installed after first packet arrives (Packet-In)Flexible; table holds only active flowsFirst packet is delayed; controller overloaded by many new flows; needs controller alive
ProactiveRules pushed before traffic comes (often wildcard rules)No delay; works even if controller is lostMust know traffic in advance; may waste table space

Reactive = asking the guide every time you enter a new room. Proactive = being handed the whole building map at the entrance.

2. The three SDN abstractions (Scott Shenker)

An abstraction means hiding messy details behind a simple view – like using a car’s steering wheel without knowing how the engine works.

Forwarding abstraction
Programs say how to forward without knowing vendor hardware. Realised by OpenFlow’s match + action rules.
Distribution abstraction
The network OS hides the hassle of many distributed devices (collecting state, failures) and gives a global network view – a graph of switches, links, hosts.
Specification abstraction
Apps state what they want on a simple view (e.g. “one big switch”). A virtualisation layer maps it to the real network.

3. OpenFlow

OpenFlow is the first standard southbound protocol – the language the controller uses to talk to switches. Proposed at Stanford in 2008, now maintained by the ONF (Open Networking Foundation). It defines (a) what a switch looks like inside and (b) the messages exchanged over the OpenFlow channel – a TCP connection to port 6653 (older: 6633), optionally secured with TLS.

3.1 Parts of an OpenFlow switch

  • Flow tables – one table in v1.0; a pipeline of tables 0…n from v1.1.
  • Group table – shared lists of actions (“buckets”) reused by many flows.
  • Meter table – per-flow speed limits for QoS (v1.3).
  • OpenFlow channel(s) – link(s) to controller(s).
  • Ports – physical, logical (tunnels, link aggregation) and reserved.

3.2 A flow entry (one rule) – remember M-P-C-I-T-C

FieldMeaning
Match fieldsWhat to compare: ingress port, MAC, VLAN, IP, TCP/UDP port, metadata… any field can be wildcarded (“don’t care”)
PriorityIf many rules match, highest priority wins
CountersPackets, bytes, duration
InstructionsWhat to do with matching packets
TimeoutsIdle: remove if unused for N seconds. Hard: remove after N seconds no matter what
CookieOpaque tag chosen by controller to find/filter entries
Flagse.g. SEND_FLOW_REM – tell controller when entry is removed

OpenFlow 1.0 match = fixed 12-tuple: ingress port, source MAC, destination MAC, EtherType, VLAN ID, VLAN priority, source IP, destination IP, IP protocol, IP ToS, source L4 port, destination L4 port. From v1.2 an extensible OXM (Type-Length-Value) match supports 40+ fields.

Rule: Match = dest IP 10.0.0.4 + TCP port 80, Priority = 100, Action = output port 3, Idle timeout = 30 s. “Web traffic to host 4 goes out of port 3; forget the rule if unused for 30 s.”

3.3 Pipeline processing

flowchart LR
P["Packet in + ingress port"] --> T0["Table 0"] --> T1["Table 1"] -->|Goto-Table| Tn["Table n"] --> E["Execute action set"] --> O["Packet out"]
T0 -.miss.-> C["Controller"]
T1 -.-> M["Meter table"]
E -.-> G["Group table"]

The packet starts at table 0. The best matching entry runs its instructions. Goto-Table can only move forward, never back. Actions can be collected into an action set that runs at the end. If no entry matches, the table-miss entry (priority 0, matches everything) decides: send to controller, drop, or go to next table. With no table-miss entry (v1.3), the packet is dropped.

3.4 Instructions and actions

InstructionEffect
Apply-ActionsDo the actions now
Write-ActionsAdd to action set (run at end)
Clear-ActionsEmpty the action set
Write-MetadataStore a note for later tables
Goto-TableContinue in a later table
MeterPass through a rate limiter

Common actions: Output to a port, Drop, Set-Field (rewrite MAC/IP/port/VLAN), Push/Pop VLAN or MPLS tag, Set-Queue (QoS), Group, Decrement TTL.

3.5 Reserved ports

PortMeaning

3.6 Group types

  • All – run every bucket → multicast/broadcast.
  • Select – run one bucket picked by hash → load balancing.
  • Indirect – one bucket, shared next hop for many flows.
  • Fast failover – run first bucket whose watched port is up → instant protection without asking the controller.
Fast failover = a road with a built-in diversion sign: if the main road is blocked, traffic switches to the side road immediately, no phone call to the control room.

4. OpenFlow messages

Controller → switch
Features-Request, Get/Set-Config, Modify-State (Flow-Mod, Group-Mod, Port-Mod, Meter-Mod), Read-State (Multipart/Stats), Packet-Out, Barrier, Role-Request
Asynchronous (switch → controller)
Packet-In, Flow-Removed, Port-Status, Error – the switch reports on its own
Symmetric (either side)
Hello, Echo request/reply, Experimenter (vendor extras)

4.1 Connection set-up

  1. Switch opens TCP (or TLS) to controller port 6653.
  2. Hello both ways – each says its highest version; the lower common one is used.
  3. Controller sends Features-Request; switch replies with its DPID (datapath ID = switch’s ID number), buffers, tables, capabilities. (Ports via multipart request in 1.3.)
  4. Controller sends Set-Config and usually installs a table-miss rule and proactive rules.
  5. Echo messages repeat to check the link is alive.

4.2 If the controller is lost

  • Fail-secure: keep using existing rules until they time out; packets needing the controller are dropped.
  • Fail-standalone: act like an ordinary learning switch (NORMAL).

4.3 Many controllers (v1.2+)

Roles: Equal (full access), Master (full access, only one), Slave (read-only, gets only Port-Status). Role-Request changes roles → quick failover between controllers.

5. OpenFlow versions

VerReleasedMain additions

Related: OpenFlow only handles forwarding rules. Configuring the switch itself (which controller, port settings) is done by OF-CONFIG (NETCONF/YANG based) or OVSDB for Open vSwitch.

If asked about “OpenFlow 1.3”, mention meters and the table-miss entry.

Topic II – SDN Controllers: Concepts, VMware, Nicira

1. What is a controller?

Software that centralises network control. It’s called a Network Operating System (NOS) because, like Windows or Linux, it manages resources (switches, links, flow tables), hides low-level details and gives services to apps. It sits between apps (above, northbound) and devices (below, southbound). In Nadeau and Gray’s idealised framework it gives a logically centralised view, accepts app requests and turns them into device instructions.

2. What every controller does

End-user device discovery
Learns hosts: MAC, IP, switch port – from ARP, DHCP or first Packet-In.
Network device discovery
Notices switches/routers connecting; reads features, ports, tables.
Topology management
Finds links by sending LLDP frames out of each port (Packet-Out) and seeing them come back as Packet-In on the neighbour; builds and updates the graph.
Flow management
Keeps flow database, computes paths, installs/changes/removes rules, collects stats.
Like a city map app: it first finds all houses (hosts), all junctions (switches), all roads (links), then plans routes (flows).
flowchart TD
A["Applications: Firewall, Routing, Monitoring, Load balancer"] --> N["Northbound API: REST, Java/Python, intents"]
N --> K["Core services: topology, inventory, host tracker, path computation, statistics, flow manager, clustering and HA"]

2.1 Internal parts

  • Northbound API – REST over HTTP, Java/Python APIs, intent interfaces.
  • Core services – topology manager, inventory, host tracker, path computation, statistics, rules manager.
  • State store – the network view; ODL uses MD-SAL with YANG models, ONOS uses distributed stores.
  • Southbound plug-ins – OpenFlow, OVSDB, NETCONF, BGP-LS, PCEP, SNMP.
  • High availability / clustering – several instances share state so one failing doesn’t stop the network.
  • Event system – apps subscribe to events (switch-connected, Packet-In, link-down).

3. VMware

VMware came to SDN from server virtualisation (many virtual machines on one server, so networking inside the server matters).

  • vSphere Distributed Switch (vDS) – one logical switch spanning many ESXi hosts. Set VLANs/policies once in vCenter, applied everywhere; a VM keeps its policy when it moves (vMotion).
  • vCloud Director and vShield – isolated tenant networks, firewalls, NAT in software.
  • VXLAN – (proposed 2011 with Cisco and others) wraps Layer-2 frames inside UDP, allowing about 16 million virtual networks over an IP network.

Early VMware did not use OpenFlow on physical switches; it controlled the virtual switches at the edge and treated the physical network as plain IP transport.

4. Nicira

Founded 2007 by Martin Casado, Nick McKeown, Scott Shenker (the people behind Ethane and OpenFlow). It created NOX (first OpenFlow controller), Open vSwitch (OVS) and the distributed controller Onix. Its product NVP (Network Virtualization Platform, 2011) was among the first commercial SDN deployments (AT&T, eBay, Rackspace).

C["NVP controller cluster"] -->|OpenFlow + OVSDB| H1["Hypervisor 1: Open vSwitch, VMs of tenants A,B"]
C -->|OpenFlow + OVSDB| H2["Hypervisor 2: Open vSwitch, VMs of tenant A"]

  • OVS in each hypervisor = programmable edge switch.
  • Controller cluster computes forwarding state per virtual network; pushes it via OpenFlow (flows) and OVSDB (config, tunnels).
  • Overlay tunnels (STT or GRE) carry virtual networks, so the physical network only needs IP connectivity.
  • Gateways link virtual networks to physical VLANs/Internet.
  • Tenants get isolated L2/L3 networks created via API in seconds.
Overlay = a private tunnel network drawn on top of the public roads. Roads (physical switches) stay unchanged; each company gets its own invisible private road system.

4.2 VMware buys Nicira → NSX

July 2012: VMware acquired Nicira for about US$1.26 billion. 2013: NVP + vCloud Networking and Security = VMware NSX (logical switches, distributed routing, distributed firewall, load balancing in the hypervisor). Seen as the moment SDN became mainstream in industry.

Topic III – The Different Controllers

Controllers differ in philosophy: some program every flow with OpenFlow, some use routing protocols, some add APIs inside existing devices.

1. NOX

First OpenFlow controller (Gude et al., 2008, Nicira). Introduced the network operating system idea. C++ core, optional Python, event-driven (handlers for datapath-join, packet-in), OpenFlow 1.0. Apps: learning switch, routing, access control. Development stopped around 2012.

2. POX

Python-only sibling of NOX by Murphy McCauley. Runs anywhere with Python, no compiling, pre-installed in the Mininet VM – the most common teaching controller. Features come as components that raise and listen to events.

C <--> D["Open vSwitch / Mininet switches"]

# Hub component
from pox.core import core
import pox.openflow.libopenflow_01 as of
def _handle_PacketIn(event):
    msg = of.ofp_packet_out(data=event.ofp)          # reply carrying the packet
    msg.actions.append(of.ofp_action_output(port=of.OFPP_FLOOD))  # send out all ports
    event.connection.send(msg)                       # send to the switch
def launch():
    core.openflow.addListenerByName("PacketIn", _handle_PacketIn)  # run on every Packet-In

3. Trema

From NEC; write controllers in Ruby (C core). Special feature: built-in network emulator, test framework and debugging tools. A controller is a Ruby class inheriting Controller with handlers like switch_ready(datapath_id) and packet_in(datapath_id, message). NEC’s ProgrammableFlow shared its heritage.

4. Ryu

“Ryu” = “flow” in Japanese. Component-based Python framework from NTT, Apache licence. Supports OpenFlow 1.0, 1.2–1.5 plus NETCONF, OF-CONFIG, OVSDB and a BGP speaker. Clean documentation, integrated with OpenStack Neutron.

from ryu.base import app_manager
from ryu.controller import ofp_event
from ryu.controller.handler import MAIN_DISPATCHER, set_ev_cls
from ryu.ofproto import ofproto_v1_3

class Hub(app_manager.RyuApp):
    OFP_VERSIONS = [ofproto_v1_3.OFP_VERSION]
    @set_ev_cls(ofp_event.EventOFPPacketIn, MAIN_DISPATCHER)  # run on Packet-In
    def packet_in(self, ev):
        msg = ev.msg; dp = msg.datapath
        ofp, parser = dp.ofproto, dp.ofproto_parser
        actions = [parser.OFPActionOutput(ofp.OFPP_FLOOD)]
        out = parser.OFPPacketOut(datapath=dp, buffer_id=msg.buffer_id,
            in_port=msg.match['in_port'], actions=actions,
            data=msg.data if msg.buffer_id == ofp.OFP_NO_BUFFER else None)
        dp.send_msg(out)
# run: ryu-manager --verbose ryu.app.simple_switch_13 ryu.app.ofctl_rest

6. Layer-3 centric controllers

Service-provider (ISP) networks care mostly about routing – IP routes, MPLS paths, VPNs. These controllers centralise that state and use routing/management protocols (BGP, PCEP, XMPP, NETCONF), not OpenFlow.

  • L3VPN controllers – hold each customer’s Layer-3 VPN model (sites, VRFs, route targets), configure Provider Edge (PE) routers via NETCONF/YANG, BGP distributes routes. Adding a site = one API call instead of configuring many routers.
flowchart LR
P["PCE server: TE database + path computation"] <-->|PCEP request/reply| H["Head-end router (PCC)"]
P -.BGP-LS topology.- R2["Router"]
H -->|RSVP-TE LSP follows computed path| R1["Router"] --> R2 --> T["Tail-end router"]
  • PCE server (RFC 4655) – computes constrained paths (bandwidth, latency, diversity) for MPLS Traffic Engineering. Routers (PCC) ask using PCEP (RFC 5440). Learns topology via IGP or BGP-LS. Stateful PCE also knows existing LSPs and re-optimises; active stateful PCE creates/changes LSPs itself.
  • Juniper Contrail / OpenContrail (later Tungsten Fabric) – controls vRouters in server hypervisors with XMPP, links to gateway routers with BGP; overlays use MPLS over GRE/UDP or VXLAN. Shows routing protocols can be the SDN control plane.
PCE = a GPS server. Routers ask “best route from A to B with enough bandwidth?”, the server answers (PCEP), and the route is set up.

7. Plexxi

Founded 2010; application-aware data-centre network. Switches joined in an optical ring called LightRail (WDM, wavelength-division multiplexing) so physical connections can change by software. Plexxi Control collects affinities – declarations of which application endpoints talk and what they need (bandwidth, low latency, isolation, path diversity) – then computes the topology and forwarding. “Affinity networking” = application-driven SDN that optimises the physical topology, not just rules. Acquired by HPE in 2018.

Big-data servers X and Y tell the network “we need a fast private path”. The fabric re-wires its optical links to give them one.

8. Cisco onePK

One Platform Kit (2012, part of Cisco ONE): an SDK exposing APIs inside IOS, IOS-XE, IOS-XR, NX-OS. It doesn’t remove the control plane; apps read and modify it. Apps in C, Java, Python run on the device, a blade, or an external server. This is the hybrid / API-driven SDN model. Cisco later moved to ACI and NETCONF/YANG.

Topic IV – Building Custom Topologies

Topology = the shape of a network (which devices connect to which). Mininet lets you describe one in Python and run it on your laptop; then you connect it to a controller and watch it work.

1. Same 5 steps for every controller

  1. Start the controller; check it listens (port 6633 old / 6653 new).
  2. Write a custom topology with Mininet’s Topo class.
  3. Start Mininet with --controller remote,ip=<IP>,port=<port> and the OpenFlow version the controller supports.
  4. Generate traffic (pingall) so the controller learns hosts.
  5. Verify switches, links, hosts, flows in CLI, REST or GUI.

2. The custom topology

# custom.py
from mininet.topo import Topo
class CustomTopo(Topo):
    def build(self):
        s1 = self.addSwitch('s1'); s2 = self.addSwitch('s2'); s3 = self.addSwitch('s3')
        h1 = self.addHost('h1'); h2 = self.addHost('h2')
        h3 = self.addHost('h3'); h4 = self.addHost('h4')
        self.addLink(h1, s1); self.addLink(h2, s1)
        self.addLink(h3, s3); self.addLink(h4, s3)
        self.addLink(s1, s2); self.addLink(s2, s3); self.addLink(s1, s3)
topos = {'custom': (lambda: CustomTopo())}
Loop warning: the three switch-to-switch links form a triangle (a loop). A broadcast (ARP) would circle forever – a broadcast storm. Use a controller with topology discovery/spanning tree, or pingall fails.
# Parameterised: chain of n switches
class LinearN(Topo):
    def build(self, n=4):
        prev = None
        for i in range(1, n + 1):
            s = self.addSwitch('s%d' % i); h = self.addHost('h%d' % i)
            self.addLink(h, s)
            if prev: self.addLink(prev, s)
            prev = s
topos = {'linearn': LinearN}
# sudo mn --custom linearn.py --topo linearn,6 --controller remote

7. Click modular router

From MIT (Kohler, Morris, Chen, Jannotti, Kaashoek, 2000). A router is built from small packet-processing blocks called elements (FromDevice, Classifier, CheckIPHeader, LookupIPRoute, Queue, ToDevice) joined in a graph written in the Click language. To change behaviour, rewrite the graph, not the code. It shows data-plane programmability and influenced Open vSwitch and P4.

FromDevice(eth0) -> Queue(1000) -> ToDevice(eth1);
Click = LEGO. Each brick does one packet job; you snap bricks together to make a router.

Controller = a restaurant kitchen. North = customers’ orders (apps). South = instructions to cooks (devices). East–west = talking to other kitchens.

1. Southbound (SBI)

Connects controller to network devices. Carries instructions down (rules, config) and events/stats up (Packet-In, port status, counters). ONF calls it CDPI (Control-Data Plane Interface). Two groups: control/forwarding protocols (OpenFlow, P4Runtime) and management/configuration protocols (NETCONF, OVSDB, OF-CONFIG, SNMP).

Many plug-ins let a controller manage new SDN switches and old routers – vital for gradual migration (ODL, ONOS).

2. Northbound (NBI)

Lets apps, orchestrators (OpenStack) and OSS/BSS use controller services (topology, host locations, path set-up, stats) without knowing devices. Not standardised – every controller has its own API. ONF’s Northbound Interface working group (2013) pushed intent-based interfaces instead.

Levels of abstraction

flowchart TD
I["Intent / policy: video from branch to DC under 50 ms"] -->|translated by controller| S["Service level: create VPN, apply QoS class"]
S -->|translated| N["Network level: compute path, reserve bandwidth"]
N -->|translated| D["Device level: install flow/config on each switch"]

Higher level = app knows less, controller translates more. With an intent, if a link fails the controller recompiles it and repairs the path automatically.

Device level = telling a taxi “turn left, then right”. Intent = “take me to the airport in 30 minutes”.

SDN programming languages

Frenetic, Pyretic (composable policies in Python), NetKAT (formal algebra for verification), Procera (event-driven policies), Maple (algorithmic policies); P4 is for the data plane. They let you combine modules (monitoring + routing) without conflicting rules.

3. East–west

One controller can’t give enough reliability or scale, and big networks split into administrative domains, so controllers must talk to each other.

flowchart LR
subgraph Cluster["ONOS / ODL cluster (one logical controller)"]
I1["Instance 1 (leader)"] <-->|Raft| I2["Instance 2"] <-->|Raft| I3["Instance 3"]
end
I2 <-->|SDNi / BGP| X["Controller of another domain"]
  • Inside a cluster: ONOS shares a distributed core; strong-consistency data (mastership, intents) uses Raft via Atomix; topology uses faster eventually consistent stores. Each switch has one master + backups; if the master dies, a backup takes over. ODL uses Akka clustering with Raft replication (typically 3 members). Cluster protocols are internal, not standardised.
  • Between domains: SDNi (IETF draft, in ODL) shares reachability, topology, capabilities; BGP (everyone speaks it); ALTO shares network-cost maps; hierarchical designs put a parent orchestrator above domain controllers.
  • East vs west: common usage: westbound = to other SDN controllers; eastbound = to legacy non-SDN networks (BGP etc.). Some authors reverse this – state your definition in answers.
Design issueExplanation
ConsistencyStrong (consensus) = safe but slower; eventual = faster but views may briefly differ
ScalabilitySplit switches among instances
AvailabilityMastership hand-over; avoid split-brain
InteroperabilityNo standard → multi-vendor federation is hard
Security/trustAuthenticate peers; limit what is revealed

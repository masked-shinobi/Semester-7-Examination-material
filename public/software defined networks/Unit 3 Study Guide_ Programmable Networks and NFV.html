Topic I: Network Programmability

Network programmability means running a network using software and APIs (a way for one program to give orders to another) instead of typing commands into every device by hand.

1. The problem with old networks

Every router or switch has two jobs: the control plane (the brain: decides where traffic should go, using protocols like OSPF and BGP) and the data plane (the muscle: actually forwards packets). In old networks each box has both, and you set each box up one by one using a vendor-specific CLI (command-line interface).

Example: Imagine a city where every traffic signal decides alone, and to change a rule a worker must visit each signal. That is a traditional network. Programmable networks are like one control room that sees the whole city and updates all signals at once.

Problems: slow and error-prone changes; vendor lock-in; no global view (each device sees only its neighbours); new protocols need new firmware or hardware; cloud data centres change too fast for manual work.

2. SDN: Software Defined Networking

SDN (defined by the Open Networking Foundation, ONF) pulls the control plane out of the boxes and puts it in one software controller that controls many simple forwarding devices. It has three planes:

  • Application plane: apps saying what the network should do (routing, firewall, load balancing, monitoring).
  • Control plane: the SDN controller (ONOS, OpenDaylight, Ryu, Floodlight). It holds the global view and turns app requests into device rules.
  • Data plane: physical and virtual switches (Open vSwitch, white-box switches) that just forward packets.

3. OpenFlow: the first southbound protocol

Proposed at Stanford in 2008, now run by ONF. The controller talks to each switch over the OpenFlow channel: a TCP connection on port 6653 (older versions used 6633), optionally secured with TLS.

An OpenFlow switch has: flow tables (a pipeline of tables, from OpenFlow 1.1), a group table (shared actions like multicast and fast failover) and a meter table (per-flow rate limits for QoS, from 1.3).

Flow entry fieldMeaning
Match fieldsWhat to look for: ingress port, MAC, VLAN, IP, TCP/UDP ports
PriorityWhich entry wins if several match
CountersPackets and bytes matched
InstructionsWhat to do: forward, drop, change headers, go to another table
TimeoutsIdle and hard timeout after which the entry is removed
CookieA tag set by the controller to identify entries

How a packet is handled: it is matched against table 0; the highest-priority match runs its instructions (maybe moving on to later tables). If nothing matches, the table-miss entry decides, usually “send to controller” or “drop”.

4. Model-driven programmability

Instead of typing CLI text, devices are configured using data models. A good way to remember it: YANG says what can be configured; NETCONF, RESTCONF and gNMI say how it is carried.

NameCarried overUse
NETCONF (RFC 6241)SSH, XMLConfigure devices with a candidate copy, validation, commit and rollback
YANG (RFC 7950)A modelling languageDescribes the settings and state of a device (OpenConfig, IETF models)
RESTCONF (RFC 8040)HTTPS, JSON or XMLWeb-style (REST) access to YANG data
gNMI / gRPCHTTP/2, Protocol BuffersConfiguration and fast streaming telemetry (live measurements)
P4RuntimegRPCFills the tables of P4 switches while they run
Remember the pairs: NETCONF + YANG for configuration, gNMI for telemetry, OpenFlow / P4Runtime for forwarding rules.

5. P4: programming the data plane itself

OpenFlow can only match headers it already knows. P4 (Programming Protocol-independent Packet Processors, 2014) lets you define how the switch itself reads and processes packets, even brand-new header types.

flowchart LR
I(["Packet in"]) --> P["Parser: read headers"] --> G["Ingress match-action"] --> T["Traffic manager"] --> E["Egress match-action"] --> D["Deparser: rebuild packet"] --> O(["Packet out"])
R["Controller fills tables via P4Runtime"] -.-> G

A P4 program has a parser (which headers exist, how to extract them), match-action tables (what to match, what to do) and a deparser (put the packet back together). It runs on a P4 target: BMv2 software switch, Intel Tofino ASIC or a SmartNIC. Uses: in-band network telemetry (INT), custom load balancing, new tunnelling protocols.

Example: OpenFlow is choosing from a fixed menu. P4 is writing your own recipe.

6. Automation and intent-based networking

  • Python libraries: Netmiko (SSH to devices), NAPALM (same commands for many vendors), ncclient (NETCONF), requests (REST).
  • Ansible: agentless automation using YAML “playbooks” (a to-do list the tool runs on many devices).
  • NetDevOps (CI/CD for networks): configs stored in Git, tested and deployed automatically.
  • Intent-based networking (IBN): you state the goal, such as “isolate guest Wi-Fi from finance servers”; the system works out the config, deploys it and keeps checking it.

Benefits: speed and automation, fewer human errors, consistent policy, vendor independence, fine-grained traffic control, faster innovation.

Topic II: Network Function Virtualization (NFV)

A network function is a job done in the network: firewall, router, load balancer, NAT, DPI (deep packet inspection), EPC (the 4G core), IMS (voice). NFV moves these jobs from dedicated hardware boxes into software, called VNFs (Virtual Network Functions), running on ordinary servers (COTS = commercial off-the-shelf).

Example: Old way: buy a separate gadget for each job (camera, calculator, radio). NFV is a smartphone: one device, many apps.

Origin: in October 2012, thirteen telecom operators published a white paper. ETSI then created the NFV Industry Specification Group (ISG), which defines the architecture.

Why needed: hardware appliances meant high cost, power and space; long delays to launch services; quick end-of-life; hard to scale for peaks.

Benefits: lower CAPEX (buying cost) and OPEX (running cost); new services in minutes; elastic scaling; open multi-vendor ecosystem; easier testing and upgrades; resilience through healing and migration.

NFVSDN
Virtualise network functionsSeparate control from data plane
Targets middleboxes and servicesTargets packet forwarding and routing
Runs on servers and cloudRuns on switches plus a controller
Standard body: ETSIONF, IETF
Independent but complementary: SDN connects and chains the VNFs.

ETSI NFV architecture

  1. VNFs and EMs: the software functions; an Element Manager does FCAPS (Fault, Configuration, Accounting, Performance, Security) for them.
  2. NFVI (NFV Infrastructure): everything VNFs run on: hardware (compute, storage, network), a virtualization layer (hypervisor like KVM, or containers) and virtual resources.
  3. MANO (Management and Orchestration):
    • NFVO (Orchestrator): manages whole network services and resources across VIMs.
    • VNFM (VNF Manager): lifecycle of individual VNFs.
    • VIM (Virtualized Infrastructure Manager): controls NFVI resources, e.g. OpenStack or Kubernetes.
    • Repositories: NS catalogue, VNF catalogue, NFV instances, NFVI resources.
  4. OSS/BSS: the operator’s operations and business systems.
Example: A restaurant. NFVO is the owner planning the whole menu service, VNFM is the chef managing each dish, VIM is the store manager handing out ingredients and kitchen space.

Descriptors: a VNFD describes one VNF (resources, connection points); an NSD describes a service made of several VNFs and their links. TOSCA templates are common.

VNF lifecycle

flowchart LR
A["Onboard"] --> B["Instantiate"] --> C["Configure"] --> D["Scale"] --> E["Heal"] --> F["Update"] --> G["Terminate"]
  1. Onboarding: VNF package (VNFD, images, scripts) is checked and stored in the catalogue.
  2. Instantiation: VNFM asks the VIM (via NFVO) for resources and starts the VNF.
  3. Configuration: EM or VNFM applies service settings.
  4. Scaling: scale out/in (more or fewer copies) or up/down (bigger or smaller copy).
  5. Healing: failed instances restarted or replaced.
  6. Update: new versions with little disruption.
  7. Termination: resources released.

Service Function Chaining (SFC)

Traffic often must pass through several functions in a fixed order. SFC (RFC 7665) steers packets along that path. The NSH (Network Service Header, RFC 8300) is a label on the packet carrying the path ID and position; SDN controllers program the forwarding between VNFs.

flowchart LR
S(["Subscriber"]) --> CL["Classifier adds NSH"] --> F["vFirewall"] --> DP["vDPI"] --> N["vNAT"] --> I(["Internet"])
Example: Airport: check-in, then security, then passport control, always in that order.

Making VNFs fast

Software on normal CPUs is slower than special chips (ASICs), so we use: DPDK (packets handled in user space, skipping the slow kernel path); SR-IOV (a network card shares itself directly with VMs); CPU pinning, huge pages, NUMA awareness (dedicated cores and nearby memory for steady speed); hardware offload (SmartNICs, FPGAs).

VNF vs CNF, MANO tools, use cases

A VNF runs in a virtual machine. A CNF (cloud-native function) runs in containers on Kubernetes: starts faster, scales easier, and is the direction of 5G cores. MANO tools: ETSI OSM, ONAP (Linux Foundation), OpenStack Tacker.

Use cases: vCPE (virtual home/business gateway), vEPC and 5G core, vIMS, vFirewall/vRouter, vCDN, virtual RAN. Challenges: matching hardware speed, complex orchestration, multi-vendor compatibility, “five nines” reliability, security of shared infrastructure, staff skills.

Topic III: NetApp Development and Network Slicing

1. What is a NetApp?

The word has two meanings. Keep them separate in exams.

  • SDN NetApp: a program on top of an SDN controller using its northbound API: reactive forwarding, firewall, load balancer, monitoring, segment routing (on ONOS, OpenDaylight, Ryu).
  • 5G NetApp: a vertical app (car, factory, health, media) that uses 5G exposure APIs: 3GPP NEF (Network Exposure Function), CAPIF (Common API Framework, TS 23.222) and ETSI MEC (Multi-access Edge Computing) APIs, to ask for QoS, device location or a slice. European 5G-PPP projects popularised this.
flowchart TB
A["Vertical NetApps: remote health, smart factory, connected car"] --> X["Exposure layer: CAPIF, NEF, MEC APIs"]
X --> M["Edge MEC hosts"]
X --> C["5G core: AMF, SMF, UPF, PCF, NSSF"]
C --- R["RAN (gNB)"]

2. NetApp development lifecycle

  1. Requirements and design: which events, data and APIs are needed.
  2. Development: Java for ONOS, Python for Ryu, REST for NEF.
  3. Packaging: ONOS .oar bundle, container image or Helm chart.
  4. Testing: Mininet (emulated network), 5G testbeds, automated tests.
  5. Onboarding: register the app on the controller or marketplace.
  6. Deploy and operate: monitor, log, update with CI/CD.

3. Example: reactive L2 learning switch (the “hello world” of SDN)

  1. A host sends a frame, the switch has no rule and sends a Packet-In.
  2. The app remembers “source MAC is on this port” in a MAC table.
  3. Destination known? Send a Flow-Mod (match that MAC, output to that port) plus a Packet-Out for this packet.
  4. Destination unknown? Packet-Out that floods the frame to all ports.

Later packets match the rule and never reach the controller. Pattern of most SDN apps: listen to events, decide, push rules.

Example: A new student in a hostel asks everyone “who is Ravi?”. Once Ravi answers, you remember his room and go straight there next time.

4. Network slicing

A network slice is a private, end-to-end logical network (across RAN, transport and core) built on shared physical equipment, each slice tailored to a service or customer.

Example: One highway with a dedicated ambulance lane, a bus lane and a normal lane. Same road, different guaranteed behaviour.
Slice typeSSTNeedExamples
eMBB (enhanced Mobile Broadband)1Very high speed4K/8K video, AR/VR
URLLC (Ultra-Reliable Low-Latency)2About 1 ms delay, very reliableRemote surgery, factory automation
MIoT / mMTC (massive IoT)3Huge numbers of low-power devicesSmart meters, sensors
V2X (Vehicle-to-Everything)4Low delay, reliable, mobileConnected vehicles

Later 3GPP releases add more values; operators can define their own.

5. Identifying slices in 5G

  • S-NSSAI identifies one slice = SST (Slice/Service Type, 8 bits) + optional SD (Slice Differentiator, 24 bits, tells apart two slices of the same type, e.g. two eMBB slices for two companies).
  • NSSAI is a list of S-NSSAIs: requested (device asks), allowed (network grants), configured.
  • A device can use several slices at once.

6. Slice management

flowchart TB
Q["Customer service request"] --> CS["CSMF: turns the request into slice requirements"]
CS --> NS["NSMF: manages the end-to-end slice"]
NS --> R["RAN NSSMF"] --> R2["gNBs, O-RAN controllers"]
NS --> T["Transport NSSMF"] --> T2["SDN controllers: VLAN, VRF, SR"]
NS --> K["Core NSSMF"] --> K2["NFV MANO then 5G core functions"]

5G core functions: NSSF picks the slice(s) for a device; AMF (access and mobility) is usually shared by slices; SMF/UPF (sessions and user traffic) are often dedicated per slice; NEF exposes slice abilities to NetApps.

Slice lifecycle (3GPP TS 28.530): preparation (design, templates) then commissioning (create and configure) then operation (activate, monitor, modify) then decommissioning (release resources).

Role of SDN and NFV: NFV gives each slice its own functions (e.g. a UPF near the edge for URLLC). SDN gives separate transport paths, bandwidth and QoS per slice using VLANs, VRFs, segment routing or flow rules. MEC runs delay-sensitive functions at the edge. FlowVisor was an early OpenFlow tool that sat between switches and several controllers, giving each its own “slice” of flow space.

Isolation types: resource (dedicated or shared CPU, spectrum), traffic (separate forwarding via VLAN/VRF/SDN), performance (QoS guarantees), management (each tenant sees only its slice). Challenges: end-to-end orchestration, strong isolation without waste, multi-operator slices, SLA monitoring, security between slices, cost of dedicated resources.

Exam tip: definition, then slice types with SST values, then the CSMF/NSMF/NSSMF diagram, then role of SDN and NFV.

Topic IV: ONOS Deployment

ONOS (Open Network Operating System) is an open-source SDN controller from ONF, first released (Avocet) in December 2014; releases are named after birds. Written in Java on Apache Karaf (an OSGi container, so apps load and unload while running).

Design goals: high availability (cluster, no single point of failure); scalability and performance; protocol independence (core is not tied to OpenFlow; devices are reached through plug-in “providers”); modularity.

Deploying ONOS step by step

  1. Prerequisite: Ubuntu VM with Java 11 (for ONOS 2.x), or Docker.
  2. Run ONOS:
    docker run -t -d -p 8181:8181 -p 8101:8101 -p 6653:6653 --name onos onosproject/onos
    (Tarball alternative: install Java 11, extract, run bin/onos-service start.)
  3. CLI: ssh -p 8101 karaf@localhost (password karaf).
  4. Activate apps: app activate org.onosproject.openflow and app activate org.onosproject.fwd
  5. GUI: http://localhost:8181/onos/ui (user onos, password rocks).
  6. Mininet (emulated network):
    sudo mn --topo tree,2 --mac --controller remote,ip=<ONOS-IP>,port=6653 --switch ovs,protocols=OpenFlow13
  7. Test: mininet> pingall
Ports to remember: GUI/REST 8181, CLI 8101, OpenFlow 6653.

Troubleshooting (no devices in GUI): is the OpenFlow app active? Right controller IP and port 6653? Mininet using OpenFlow 1.3? Use log:tail and the GUI. Pressing H in the GUI toggles hosts.

Clustering and high availability

Run 3 or 5 ONOS nodes. Since ONOS 1.14, shared state lives in a separate Atomix cluster using the Raft consensus method (an odd number of nodes means a majority can always agree). Each switch has one master node and standby nodes. If the master fails, mastership moves and forwarding continues.

flowchart TB
SA["Switch A: master node 1, standby node 2"] --- N1["ONOS node 1"]
SB["Switch B: master node 2"] --- N2["ONOS node 2"]
SC["Switch C: master node 3"] --- N3["ONOS node 3"]
N1 & N2 & N3 --> AT["Atomix cluster (Raft): shared state"]
Example: If node 1 dies, Switch A’s standby (node 2) takes over. Like a substitute teacher stepping in.

Intent framework

An intent is what you want, not how to do it. ONOS compiles it into flow rules, installs them, and recompiles automatically if a link fails. Types: host-to-host, point-to-point, single-point-to-multipoint, multipoint-to-single-point, path.

onos> add-host-intent 00:00:00:00:00:01/None 00:00:00:00:00:02/None
onos> intents
Example: Telling a taxi “take me to the airport” (intent) rather than giving every turn. If a road is blocked, the driver picks another route.

Developing an ONOS app

  1. Generate a project with onos-create-app (Maven archetype).
  2. Write a Java component using PacketService, FlowRuleService, HostService, IntentService.
  3. Build: mvn clean install gives an .oar file.
  4. Install: onos-app <onos-ip> install! target/<app>.oar
  5. Check logs: log:tail

Topic V: OPNFV

OPNFV (Open Platform for NFV) was a Linux Foundation project launched in September 2014 to build a carrier-grade, open-source reference platform for NFV. It wrote no new stack. It integrated existing projects, tested them together, and pushed fixes upstream (to the original projects, without forking).

Example: A mechanic who takes engine, gearbox and wheels from different makers, assembles a car, test-drives it, and sends bug reports back to each maker.

Goals: an integrated, tested NFVI and VIM; carrier-grade features (high availability, fault management, performance) added upstream; common test tools and verification; interoperability and faster adoption.

Scope: NFVI and VIM (later MANO integration). VNFs themselves were out of scope.

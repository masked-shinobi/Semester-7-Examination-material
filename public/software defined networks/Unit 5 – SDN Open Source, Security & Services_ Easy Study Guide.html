An easy first-time study guide: simple words, everyday examples, diagrams and exam tips. Five topics, one page.

Normal networks: every switch and router decides for itself. SDN (Software Defined Networking): one central software “brain” called the controller decides, and the switches just follow its rules. Keep this one idea in mind through the whole unit. Rules inside a switch are called flow entries, kept in a flow table. OpenFlow is the language the controller uses to talk to switches.

Topic I – SDN Open Source and SDN Future

1. What is open source, and why does SDN love it?

Open source means the software’s code is public. Anyone can use it, read it and improve it. OpenFlow, Open vSwitch, Mininet and the big controllers are all open projects.
A restaurant that publishes its recipe lets anyone cook it, fix it, or improve it. A restaurant with a secret recipe makes you buy only from them.
No lock-in (vendor independence)
Same software runs on many vendors’ hardware.
Faster innovation
People add features instead of waiting for a company roadmap.
Lower cost
No per-port licence; cheap “white-box” switches.
Transparency
Code can be inspected, so it is easier to trust and security-check.
Interoperability
Open reference code makes the standards concrete.

4. Where SDN is heading (future trends)

  1. Programmable data planes (P4, eBPF/XDP): define new packet handling in software, without new hardware (e.g. in-band telemetry, custom load balancing).
  2. Intent-based networking: you state the goal (“keep guests away from servers”); software works out and checks the rules (closed-loop automation).
  3. AI/ML for networks (AIOps): predict traffic, spot attacks, fix problems automatically.
  4. Disaggregation: separate hardware from network OS (SONiC on white boxes).
  5. Cloud-native and edge: Kubernetes networking and Multi-access Edge Computing (MEC) move control close to users.
  6. 5G, 6G, Open RAN: programmable radio controllers and network slicing (separate virtual networks on one mobile network).
  7. SASE and SD-WAN: networking plus security delivered as cloud services.
  8. Network verification and digital twins: test a software copy of the network before changing the real one.

Topic II – SDN Security

SDN changes security in two ways. Security of SDN = protecting the controller, APIs, channels and switches (new targets). Security using SDN = using the central view and programmability to build firewalls, stop DDoS, quarantine and segment (new tools). A good answer covers both.
One master key opens every room in a building. That is convenient, but whoever steals it controls the whole building. The controller is that key.

2. Important attacks explained

Controller saturation (DoS)
In reactive mode, every packet with no matching rule is sent to the controller as a Packet-In. Attacker sends packets with random headers; the channel and controller CPU choke; real flows stall.
Flow-table overflow
Each new flow may add an entry. A flood of different flows fills the small hardware table (TCAM), so real flows cannot be installed.
Link fabrication / host location hijacking
Controllers find links using LLDP packets. A bad host forges LLDP to create fake links, or spoofs a victim’s address so traffic is pulled to the attacker. TopoGuard checks topology updates.
MITM on control channel
OpenFlow allows TLS but many leave it off, so an attacker on the path can read or inject messages.
Malicious application
Apps run with the controller’s power and can delete rules or exhaust resources. Rosemary sandboxes apps; SE-Floodlight adds permissions.
Rule inference by timing
The first packet is slower if no rule exists yet, so an attacker learns the network’s policy by measuring delay.
Controller saturation is like thousands of fake callers jamming a company’s one reception desk so real customers cannot get through.

Topic III – Switching and Load Balancers

1. How an SDN switch switches

An old switch learns which device is on which port by itself and runs STP (Spanning Tree Protocol) to avoid loops. An SDN switch has no such brain. It only matches packets against rules and acts (“match–action”).

Figure 4: Reactive learning switch

Reactive = rule created when the first packet arrives (small delay for first packet). Proactive = rules installed in advance (no first-packet delay, and works even if the controller goes down).
Reactive is asking the receptionist for directions the first time, then remembering the route. Proactive is being handed a map before you arrive.
Switch typeDescriptionTrade-off
OpenFlow-onlyForwards purely by flow tablesClean model; no legacy features
OpenFlow-hybridFlow tables plus normal L2/L3 on the same deviceGradual migration; harder to reason about
Hardware (ASIC/TCAM)Line-rate forwardingSmall flow table, costly
Software (Open vSwitch)Runs on servers/hypervisorsFlexible, large tables; slower unless accelerated (DPDK)

Advantages: loop-free paths without STP (controller computes paths, no blocked links); multipath (select-type group tables or ECMP use all links); fast failover (fast-failover group tables switch to a backup port without asking the controller); flexible matching (any header field, not just destination MAC).

2. Open vSwitch (OVS)

OVS is the standard open-source virtual switch that lives inside a server and connects virtual machines (VMs). Supports VXLAN and other tunnels, OpenFlow 1.0–1.5 and DPDK acceleration.

Figure 5: First packet takes the slow path; later packets stay in the fast kernel path

ovs-vswitchd holds OpenFlow tables and talks to the controller. ovsdb-server stores configuration (managed via OVSDB). The kernel datapath forwards using a flow cache: the first packet misses and goes up to user space, the flow is cached, and the rest are fast.

ovs-vsctl show                                  # bridges and ports
ovs-ofctl -O OpenFlow13 dump-flows s1           # list flow entries
ovs-ofctl -O OpenFlow13 add-flow s1 "priority=10,in_port=1,actions=output:2"

3. Load balancers

A load balancer shares work across many resources to raise throughput, cut response time and avoid overload. Old hardware ones (ADC – Application Delivery Controller) are costly proprietary boxes in the path. In SDN, the choice is a controller app and the switches just forward.
Supermarket with 3 checkout counters: a guide at the door sends each customer to the shortest line. Customers just see “one entrance”.
TypeBalancesSDN technique

Server load balancing with OpenFlow

Figure 6: Clients see one virtual IP; the controller installs rewrite rules

  1. Clients send to one virtual IP (VIP), 10.0.0.100.
  2. First packet reaches the switch, no rule, so Packet-In goes to the controller.
  3. Controller picks a server and installs two rules: a forward rule rewriting destination MAC and IP to the server, and a reverse rule rewriting the server’s source back to the VIP.
  4. The controller also answers ARP requests for the VIP (proxy ARP).
Like a company phone number: callers dial one number, reception forwards them to a staff member, and the reply seems to come from the company.
Remember the two-rule pattern: client→VIP becomes client→server, and server→client is rewritten back to the VIP. Idea shown by Stanford’s Plug-n-Serve; later work used wildcard rules over client-address prefixes so most connections skip the controller.
# Ryu-style logic (OpenFlow 1.3)
VIP, VMAC = '10.0.0.100', '00:00:00:00:01:00'
SERVERS = [('10.0.0.2','00:00:00:00:00:02',2), ('10.0.0.3','00:00:00:00:00:03',3)]
def pick(self):                     # round robin: next server in turn
    s = SERVERS[self.nxt]; self.nxt = (self.nxt+1) % len(SERVERS); return s
# On Packet-In for client → VIP:  ip, mac, port = self.pick()
# fwd match: ipv4_src=client, ipv4_dst=VIP
#   actions: set eth_dst=mac, set ipv4_dst=ip, output(port)
# rev match: ipv4_src=ip, ipv4_dst=client
#   actions: set eth_src=VMAC, set ipv4_src=VIP, output(client_port)
# install both with idle_timeout, send first packet out, proxy-ARP for VIP

Algorithms and health checks

  • Round robin / weighted round robin: servers take turns; weights for stronger servers.
  • Least connections / least load: pick the server with lowest counters from flow/port statistics.
  • Hash of 5-tuple (source/destination IP, ports, protocol): one flow always goes to the same server (affinity).
  • Wildcard split: divide client address space into prefixes, one per server.
  • Health monitoring: the controller pings or TCP-checks servers or watches port status, removes failed servers and reinstalls rules. Existing connections to the failed server are reset or re-mapped.

Advantage over hardware ADC: commodity switches, programmable policy, global view of server and link load.

ChallengeRemedy
Controller handles every new connectionWildcard and proactive rules; per-flow rules only when needed
Limited flow-table sizeAggregate rules, short idle timeouts

Topic IV – Firewall and Access Control

A firewall decides which traffic may enter, leave or cross a network. Access control decides who or what may use which resource. SDN turns both into flow rules managed from one controller.
Firewall = security guard checking every bag at the gate. Access control = the ID card deciding which floors you can enter.

1. Firewall types

TypeWorks onRemarks
Packet filterHeader fields of each packet (L3/L4)Fast, stateless, simple ACLs
StatefulConnection stateAllows replies to established connections
Application / proxyApplication dataDeep inspection, slower
Next-Generation (NGFW)Applications, users, threatsCombines DPI (Deep Packet Inspection), IPS (Intrusion Prevention System) and identity
Distributed / hostEach host or hypervisor switchPolicy close to the workload

Traditional firewalls sit at the edge (perimeter), so traffic inside (east–west) is unprotected and rules are set box by box.

2. Firewall with SDN

An OpenFlow switch can match ingress port, MAC, VLAN, IP, protocol and TCP/UDP ports. A rule with no output action drops the packet; with an output action it allows. Priority settles overlaps. No match (table-miss) goes to the controller’s firewall app, which installs an allow or deny rule.

Figure 7: Firewall rules as prioritised flow entries; higher number wins

  • Controller application: Floodlight Firewall, ONOS ACL app or custom Ryu app keeps a rule list and installs flow entries.
  • Switch-resident / virtual firewall: rules enforced in Open vSwitch on each hypervisor (distributed firewall), or a firewall VNF (Virtual Network Function) in a service chain.
  • Stateful behaviour: OpenFlow 1.3 is stateless. The controller fakes state: when an inside host opens a connection it temporarily installs the reverse rule (idle timeout) so replies pass while unsolicited inbound packets stay blocked. OVS connection tracking or P4 gives real state.
ovs-ofctl -O OpenFlow13 add-flow s1 "priority=100,tcp,nw_dst=10.0.0.2,tp_dst=80,actions=drop"
ovs-ofctl -O OpenFlow13 add-flow s1 "priority=1,actions=normal"   # allow the rest
# Floodlight firewall (REST)
curl -X PUT  http://127.0.0.1:8080/wm/firewall/module/enable/json -d ''
curl -X POST http://127.0.0.1:8080/wm/firewall/rules/json \
  -d '{"src-ip":"10.0.0.1/32","dst-ip":"10.0.0.2/32","nwproto":"ICMP","action":"DENY"}'
# Mininet test:  h1 ping -c2 h2 (blocked)   h3 ping -c2 h2 (allowed)

3. Access control

Began with Ethane (Stanford, 2007): a central controller authenticated users/hosts and approved every new flow against a global policy. It is the direct ancestor of OpenFlow.

Figure 8: Identity-based access control with 802.1X, RADIUS and an SDN controller

  1. Device logs in with IEEE 802.1X; the access switch relays the request.
  2. A RADIUS (Remote Authentication Dial-In User Service) or identity server checks credentials.
  3. The controller receives the user’s role or group.
  4. The controller installs rules (or assigns a VLAN or slice) for that role.
  5. Only permitted traffic flows; on logout or alert the rules are removed or tightened.

Role-based (RBAC)User’s roleStudents: Internet only; staff: file servers

4. Policy conflicts and tools

  • Shadowing: a higher-priority rule hides a lower one (the lower rule never fires).
  • Redundancy: a rule has no effect.
  • Correlation: overlapping rules with different actions.
  • Generalisation: one rule is a broader version of another.
FlowGuard
Detects and resolves firewall violations and conflicts
FortNOX
Checks rules from different apps for conflicts
VeriFlow
Verifies rules before installing
FRESCO
Build security functions as reusable OpenFlow modules

5. Design guidelines

  • Lowest-priority default-deny rule for sensitive zones, then explicit allows.
  • Idle timeouts on dynamic allow rules so the table does not fill.
  • Aggregate rules by prefix and protocol.
  • Log denied flows (send to controller or mirror to a collector).
  • Chain an NGFW or IDS for traffic needing deep inspection.
State the weakness: SDN firewalls are mostly L2–L4 and flow-level; deep inspection needs an NGFW or IDS in a service chain.

Topic V – Use Cases in Legacy Network Security

Legacy network = routers and switches with built-in distributed control, configured one by one through CLI (Command-Line Interface), SNMP or NETCONF. They cannot be replaced overnight, so SDN augments them, not only replaces them.

1. Weaknesses of legacy networks

  • Policy spread over many boxes, so inconsistent ACLs and firewall rules leave gaps.
  • Reaction to attacks is manual and slow.
  • Visibility is local; correlating events is hard.
  • East–west traffic rarely inspected; flat networks let malware spread.
  • Old protocols (Modbus, DNP3) have no authentication.

2. How SDN is applied

  • Controller as management overlay: collects telemetry (sFlow, NetFlow, SNMP) and applies decisions through CLI, NETCONF or vendor APIs (push ACLs, shut ports, change VLANs).
  • Hybrid SDN: SDN-capable switches or ports sit alongside legacy devices and take over specific security jobs.

Figure 9: One security controller managing legacy devices and SDN switches together

3. Use cases

(a) DDoS mitigation
Legacy: RTBH (Remotely Triggered Black Hole) drops all traffic to the victim address; BGP FlowSpec (RFC 8955) distributes filter rules to routers. SDN detects the attack from flow stats, pushes FlowSpec/ACL rules or diverts victim traffic through a scrubbing centre, restoring service automatically.
(b) NAC for existing switches
Network Access Control: switches authenticate with 802.1X or MAB (MAC Authentication Bypass). Controller gets identity from RADIUS and applies the role by dynamic VLAN, downloadable ACLs or RADIUS Change of Authorization (RFC 5176), so policy follows the user.
(c) Quarantine
IDS or endpoint tool alerts; controller shuts the port, moves host to a remediation VLAN or installs a drop rule, containing worms and ransomware in seconds.
(d) Targeted inspection
Instead of mirroring all traffic (SPAN) to the IDS, redirect only suspicious flows or chosen protocols to the IDS or honeypot.
(e) ICS / SCADA security
OT (Operational Technology) networks use protocols that cannot authenticate. Segment zones (IEC 62443 zones and conduits) and whitelist permitted flows; anything else is dropped and reported.
(f) Policy consolidation
One high-level policy in the controller is translated into many device ACLs, removing inconsistency across hundreds of firewalls and switches.
(g) Visibility and forensics
Flow stats and sampled data (sFlow/NetFlow) collected centrally give a network-wide picture and a record for investigation.
Blackholing with RTBH is like locking the shop’s front door because a mob is outside: the attack stops but real customers cannot enter. SDN diversion is like a bouncer who turns away only the troublemakers.

4. Hybrid SDN migration models

Port-based
Some ports of a switch run OpenFlow, others stay legacy.
Topology-based
SDN “islands” inside the legacy network. Panopticon research: a few SDN switches give most of the benefit.
Service-based
Legacy routing for normal traffic; SDN only for chosen services like firewalling.
Traffic-class based
Some traffic classes follow SDN rules, others legacy forwarding.
Fail modes (controller lost): fail-secure keeps existing rules and drops unmatched traffic. Fail-standalone falls back to normal switch forwarding. Security-critical zones choose fail-secure.

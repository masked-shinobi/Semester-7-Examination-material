0 · Start here: words you must know first

A network is computers connected so they can send data. Data travels in small chunks called packets. Switches and routers are the boxes that pass packets along, like road junctions that point cars in the right direction.

Example – a city. Packets are cars. Routers/switches are junctions. Each junction needs to know two things: (1) which road should this car take? (a decision) and (2) actually push the car onto that road (an action). Everything in this unit is about who makes the decision.
Control plane = the brain. Decides where packets should go. Slow but clever. Runs routing protocols.
Data plane = the muscle. Moves each packet quickly using the brain’s table. Fast but simple.
Management plane = the office. Humans configure and monitor the device (CLI, SNMP).
Example – a taxi. Control plane = the map and route planning. Data plane = the driving. In an old network every taxi plans its own route. In SDN one dispatcher plans routes for all taxis and just tells them “turn left here”.

Common short forms: CLI = typing commands into a device. API = a way for programs to talk to each other. ASIC = a special fast chip inside switches. VM = a virtual (software) computer.

Topic 1 · Introduction & Evolution of SDN

1.1 What is SDN?

Definition (write this in exams): SDN is a network design where the control plane is separated from the data plane, one logically centralised controller (software) controls many switches, and the network is programmable through open APIs.

Three ideas inside it:

  • Separation of planes – the thinking is moved out of the switch into software; the switch only forwards.
  • Logically centralised control – one controller (or a team of controllers acting as one) sees the whole network.
  • Programmability – you change the network by writing a program, not by typing on each device.
Example. A college has 80 switches. Old way: log in to all 80 to block a website. SDN way: write one rule in the controller; it pushes the rule to all 80.

  • Control layer – the controller. Keeps topology (the map), computes paths, turns requests into rules. Examples: OpenDaylight, ONOS, Ryu, Floodlight, POX.

1.4 Key terms

  • Flow – a stream of packets with the same header values (e.g. same source/destination IP and port). Like all cars going from your house to the office.
  • Flow table – a list inside the switch: “if packet looks like X (match), do Y (action)”. The controller fills it.
  • Network OS (NOS) – controller software giving apps a global view, like Windows gives apps a view of a computer.
  • SDN datapath – the forwarding switch.
  • SDN application – program stating desired behaviour.

1.8 Benefits and challenges

Benefits
  • Central management
  • Automation (minutes, not days)
  • Lower CAPEX (cheap white-box switches) and OPEX (less manual work)
  • No vendor lock-in
  • Fast innovation (new feature = new software)
  • Fine-grained per-flow control
  • Network virtualisation
Challenges
  • Controller can be a single point of failure (use clusters)
  • One controller may not scale
  • Latency: first packet of a new flow waits for controller
  • Controller is a security target
  • Migrating from old networks
  • Skills gap

Topic 2 · Need for SDN

After ~2005 apps, users and data centres changed fast, but networks were still set up box by box.

2.1 Four trends (the causes)

flowchart LR
T1["Changing traffic
(east–west)"] --> L
T2["Consumerisation of IT
(BYOD)"] --> L
T3["Cloud services"] --> L
T4["Big data"] --> L
L["Limits of old networks:
complexity · inconsistent policy ·
can’t scale · vendor dependence"] --> N["NEED FOR SDN"]
  • Changing traffic patterns – old: north–south (user ↔ one server). Now: east–west (server ↔ server inside the data centre).
    Example: opening one shopping page makes the web server ask the database, payment server, recommendation server and stock server – lots of internal chatter. Old tree-shaped networks jam up.
  • Consumerisation of IT / BYOD (Bring Your Own Device) – phones and laptops of staff join the network; each needs the right access, applied dynamically.
  • Rise of cloud – you can create a server in seconds, but the network (VLANs, ACLs, firewalls) still needed manual setup. Also multi-tenancy: many customers share hardware yet must stay isolated.
  • Big data – thousands of servers exchange huge data (Hadoop/MapReduce); needs massive bandwidth, any-to-any.

2.2 Four limitations of traditional networks

LimitationMeaning
Complexity → stasisMany protocols; adding or moving a device means hand-editing switches, routers, firewalls, ACLs, VLANs, QoS. Changes are risky, so people avoid them and the network stays frozen.
Inconsistent policiesOne policy must be typed on thousands of devices; one mistake = security hole.
Inability to scaleBuilt for predictable traffic (over-subscription); cloud/big-data traffic is unpredictable.
Vendor dependenceNew features wait 3+ years for vendor releases; no open interface.

2.3 Data-centre problems

  • VLAN limit – VLAN ID is 12 bits → only 4094 usable VLANs. A cloud with 20,000 tenants can’t give each its own.
  • Spanning Tree Protocol (STP) – blocks backup links to prevent loops, so up to half the capacity sits idle.
    Like closing half the roads in a city to avoid traffic circles.
  • VM mobility – a VM moves to another server; its address, ACLs, QoS must follow instantly.
  • MAC table explosion – thousands of VMs overflow switch address tables.
  • Manual provisioning – days for a new tenant network while a server takes minutes.

2.4 Other pressures

  • Ossified Internet – researchers couldn’t test new protocols on real closed networks. This led to GENI testbed and Stanford’s Clean Slate → Ethane → OpenFlow.
  • Economics – CAPEX (buying proprietary kit) and OPEX (people time); SDN uses cheap merchant-silicon white-box switches and automation.
  • Others: agility (services in hours), visibility (global view), security (network-wide response), traffic engineering (best use of links).

2.5 Requirements of a modern network

AdaptabilityAutomationMaintainabilityModel managementMobilityIntegrated securityOn-demand scaling

2.6 How SDN solves each need

ProblemSDN answer
ComplexityCentral controller + APIs automate
Inconsistent policyDefine once, push everywhere
Scale / multi-tenancyOverlay networks (VXLAN: ~16 million IDs), flow-based forwarding, no STP
Vendor lock-inOpenFlow + commodity switches
Slow innovationNew features = apps
No visibilityController knows topology, hosts, statistics
Poor link useCentral traffic engineering – Google B4 runs WAN links near 100%

Who uses it: data centres (multi-tenancy), carriers (bandwidth on demand), campuses (BYOD, guest isolation), researchers (test protocols).

Exam tip: answer = 4 trends (cause) → 4 limitations (problem) → SDN solution table.

Topic 3 · Centralized & Distributed Control and Data Planes

Separating control from forwarding is evolution, not revolution: routers already had a separate route processor and line cards, and phone networks separated signalling (SS7) from voice.

3.1 The three planes

PlaneJobRuns onSpeed
DataLook up header, pick port, reduce TTL, rewrite MACASIC, NPU, TCAMLine rate (nanoseconds)
ControlLearn topology, run OSPF/IS-IS/BGP/LDP/STP, build tablesRoute-processor CPUms–seconds
ManagementConfigure, monitor (CLI, SNMP, NETCONF)CPUHuman speed

TTL = Time To Live, a counter that stops packets circling forever. TCAM = very fast lookup memory.

3.2 Moving information between planes

subgraph RP["Route processor (control + management plane)"]
P["Routing protocols
OSPF · IS-IS · BGP"] --> RIB["RIB

end
subgraph LC["Line cards (data plane)"]
F["FIB + ASIC
best routes only"]
end
RIB -- "install best routes ↓" --> F
F -. "punt exceptions ↑" .-> P
  • Down (control → data): protocols fill the RIB (Routing Information Base – all routes). The best route per destination goes to the FIB (Forwarding Information Base) on each line card for fast lookup.
  • Up (punt path): most packets never touch the CPU. Exceptions are “punted”: routing-protocol packets, SSH/SNMP to the router, TTL-expired packets (to send ICMP reply), ARP, unknown destinations, IP options. Punting is rate-limited (Control Plane Policing) to protect the slow CPU.
  • In OpenFlow the same idea is the Packet-In message: no rule matches → send packet to the controller.
Example: RIB = a big phone book of all contacts; FIB = your speed-dial list of only the best number for each person.

3.4 Distributed control plane

Every device runs its own control plane and they swap information to agree. The Internet is the biggest example.

  • IP underlay: an IGP (OSPF or IS-IS) floods link information so every router builds the same map and runs Dijkstra’s Shortest Path First (SPF). BGP carries external/customer routes (often via route reflectors).
  • MPLS overlay: packets get short labels (via LDP or RSVP-TE) and follow Label Switched Paths (LSPs). Provider Edge (PE) routers keep one VRF table per customer and share VPN routes with MP-BGP → Layer-3 VPN.
    Like a private lane on the highway for each company.

PropertyHow it works
Convergence timeAfter a failure: detect → flood → recompute SPF → update FIB. Meanwhile micro-loops/black holes can occur. Fast Reroute shrinks it to tens of ms.
Load balancing (ECMP)Equal-Cost Multi-Path hashes flows across equal-cost paths; it doesn’t see real link load.
High availabilityRedundant route processors, Graceful Restart, Non-Stop Routing, ISSU. Data plane keeps forwarding while control restarts.
ReplicationMulticast trees (PIM) or ingress replication copy packets to many receivers.
ScalabilityAreas, route summarisation, BGP route reflectors

Strengths: no single point of failure, proven at Internet scale. Weaknesses: only local view, hard to optimise globally, box-by-box setup, slow innovation, inconsistent states during convergence.

3.5 Centralised control plane

LiteralLogical
MeaningExactly one physical controllerSeveral instances sharing state, acting as one
FailureSingle point of failureSurvives failures (replication, leader election)
ScaleLimited by one serverAdd more instances
ExamplesEarly NOX, lab POXONOS, OpenDaylight clusters, Google B4, Onix

Earlier centralised designs:

  • ATM LANE – Ethernet-style LANs over connection-oriented ATM. LECS (configuration server: which LAN to join), LES (maps MAC → ATM address, LE-ARP), BUS (handles broadcast/unknown traffic); clients are LECs. Servers were bottlenecks and single points of failure.
  • Route servers at IXPs – each member peers with one route server over BGP instead of a full mesh.
    300 members: full mesh needs ~45,000 sessions; with a route server just 300. Traffic still flows directly between members.
  • RCP – central server computed BGP routes for all routers in AT&T’s network.
  • SDN controller – computes paths from global topology; installs flow entries proactively (before traffic) or reactively (on Packet-In).

3.6 Comparison and hybrid

AspectDistributedCentralised
DecisionsIn every deviceIn controller
ViewLocalGlobal
ConsistencyAfter convergenceController updates in planned order
OptimisationShortest path, ECMPGlobal traffic engineering

FailureVery robustNeeds controller replication
InnovationNeeds new standardsNew apps

Hybrid: real networks mix both – distributed protocols for basic reachability and fast failover, a central controller (PCE, Google B4 TE server) for optimisation.

Topic 4 · The Genesis of SDN

SDN didn’t appear suddenly in 2008. Feamster, Rexford & Zegura (The Road to SDN, 2014) describe three overlapping phases.

flowchart LR
A["PHASE 1
Active networking
mid-90s–early 2000s"] --> B["PHASE 2
Control/data separation
2001–2007"] --> C["PHASE 3
OpenFlow + Network OS
2007–2010"]

Phase 1 – Active networking

Idea: make the network programmable by running code inside nodes (funded by DARPA). Motivation: standards took too long, and middleboxes (firewalls, proxies) were each configured separately.

Capsule model
Code travels inside packets (in-band). Example: ANTS (MIT).
Programmable router model
Operator installs code in nodes (out-of-band); header picks the program. Examples: SwitchWare (Penn), NetScript, Smart Packets.
Example: Capsule = a parcel that carries its own instructions. Programmable router = instructions installed in the post office beforehand; the label on the parcel selects which to use.

Contributions: programmable functions; network virtualisation (early slicing); unified middlebox control (today’s NFV). Why not adopted: no urgent problem solved, performance/security worries, vendors had no incentive.

Phase 2 – Separating control and data planes (2001–2007)

ISPs needed better traffic engineering; before this they only tweaked protocol weights.

ProjectIdea
ForCES (IETF, 2003, RFC 3746/5810)Standard protocol between Control Elements and Forwarding Elements inside a device; vendors didn’t adopt it
RCP (2004, AT&T/Princeton)Central server computes BGP routes for an AS, pushes via iBGP – works with existing routers
SoftRouter (Bell Labs, 2004)Control-element servers manage many forwarding elements
4D (2005)Four planes: Decision, Dissemination, Discovery, Data
PCE (IETF 2006, RFC 4655)Server computes MPLS-TE paths
SANE / Ethane (Stanford 2006–07)Central controller enforces policy with simple flow switches
flowchart TB
D1["Decision plane – network-wide decisions"] <--> D2["Dissemination plane – delivers decisions"] <--> D3["Discovery plane – finds devices/links"] <--> D4["Data plane – forwards packets"]

Ethane (Casado 2007) = direct ancestor of OpenFlow. Every new flow went to a central controller that checked a policy written for users and hosts (not IPs); if allowed, it installed flow entries along the path. Switches were simple: flow table + secure channel. Deployed in Stanford’s CS department.

Example: a building security desk. Every new visitor (flow) is checked once by the guard (controller); then the gate (switch) lets them pass without asking again.

Contributions: logically centralised control with an open interface; distributed state management (led to Onix, ONOS). Limited adoption: vendors had no incentive; RCP was stuck with BGP.

Phase 3 – OpenFlow & Network OS (2007–2010)

flowchart LR
E["Ethane 2007"] --> O["OpenFlow paper 2008
McKeown et al."] --> N["NOX 2008"] --> V["OpenFlow 1.0
Dec 2009"] --> F["ONF
Mar 2011"]
  • OpenFlow – switch abstraction = flow table (match fields + counters + actions: forward, drop, send to controller, modify). Controller installs entries over a secure channel. Many switches already had ACL-like tables, so a firmware upgrade was enough.
  • NOX (2008) – first OpenFlow controller / network OS. FlowVisor (2009) – slices a network among controllers (used in GENI). Onix (2010) – distributed controller platform (Nicira, Google, NEC). Mininet (2010) – emulator.
  • Why OpenFlow won: works on existing hardware; simple match–action abstraction; immediate needs (campus research, data centres); open-source tools (NOX, OVS, Mininet); ONF support – founded March 2011 by Deutsche Telekom, Facebook, Google, Microsoft, Verizon, Yahoo!.
  • Contributions: one abstraction for switch/router/firewall/NAT/load balancer; the network-OS vision; reliable distributed controllers.

Network virtualisation

Many logical networks on one physical network (VINI testbed, Nicira NVP). Neither needs nor depends on SDN, but SDN made it easy; it was SDN’s first big commercial use (Nicira bought by VMware, 2012).

Quick timeline

1995–2000 active networking (ANTS, SwitchWare, NetScript) · 2003 ForCES · 2004 RCP, SoftRouter · 2005 4D · 2006 PCE, SANE · 2007 Ethane · 2008 OpenFlow, NOX · 2009 OpenFlow 1.0, FlowVisor · 2010 Onix, Mininet · 2011 ONF.

Topic 5 · Mininet & SDN in Mininet

5.1 What is Mininet?

A network emulator: builds a whole virtual network (hosts, switches, links, controllers) on one Linux computer. Made at Stanford (Lantz, Heller, McKeown, 2010, A Network in a Laptop). It runs real Linux software and real OpenFlow switches, so code usually moves to real hardware unchanged.

ApproachLimit compared to Mininet
Simulator (ns-3, OMNeT++)Models protocols; doesn’t run real controller/app code
Full VMsHeavy; only a few per machine
Hardware testbedCostly, slow to rewire
MininetReal code, hundreds of nodes, starts in seconds

5.2 How it works

flowchart TB
C["Controller
(reference / POX / Ryu / ONOS)"] -- "OpenFlow over TCP 6653" --> S["Open vSwitch s1
ports s1-eth1, s1-eth2"]
S -- "veth pair" --> H1["Host h1 (namespace)
h1-eth0 · 10.0.0.1"]
S -- "veth pair" --> H2["Host h2 (namespace)
h2-eth0 · 10.0.0.2"]
  • Hosts – ordinary Linux processes in their own network namespace (own interfaces, IP, routing and ARP table) but sharing the kernel. This “process-based virtualisation” is why it’s light.
  • Links – veth (virtual Ethernet) pairs, like a virtual cable. Linux tc (traffic control) sets bandwidth, delay, loss.
  • Switches – Open vSwitch (OVS, kernel mode ovsk, OpenFlow 1.0–1.5); alternatives: user-space switch, Linux bridge.
  • Controllers – built-in, OVS controller, or any remote one (POX, Ryu, ODL, ONOS, Floodlight).

  2. Native from source:
git clone https://github.com/mininet/mininet

  1. Package: sudo apt-get install mininet openvswitch-switch (may be older).

5.6 Implementing SDN in Mininet

Experiment 1 – Separation of planes (no controller). An empty switch drops everything, so we act as the controller by hand:

sudo mn --topo single,2 --mac --controller none
mininet> h1 ping -c 2 h2     # fails
mininet> sh ovs-ofctl add-flow s1 in_port=1,actions=output:2
mininet> sh ovs-ofctl add-flow s1 in_port=2,actions=output:1
mininet> h1 ping -c 2 h2     # works
mininet> sh ovs-ofctl dump-flows s1   # n_packets increasing

Proves the switch only forwards; decisions come from outside. A rule like dl_type=0x0800,nw_dst=10.0.0.2,actions=drop makes a simple firewall.

Experiment 2 – Reactive control with POX.

# terminal 1
cd ~/pox
./pox.py log.level --DEBUG forwarding.l2_learning
# terminal 2
sudo mn --topo tree,depth=2,fanout=2 --controller remote,ip=127.0.0.1,port=6633

Experiment 3 – Custom topology (Python):

from mininet.topo import Topo
class MyTopo(Topo):
    "Two switches, two hosts on each"
    def build(self):
        s1 = self.addSwitch('s1'); s2 = self.addSwitch('s2')
        for h, s in (('h1',s1),('h2',s1),('h3',s2),('h4',s2)):
            self.addLink(self.addHost(h), s)
        self.addLink(s1, s2, bw=10, delay='5ms')
topos = {'mytopo': (lambda: MyTopo())}
# run: sudo mn --custom mytopo.py --topo mytopo --link tc --controller remote

Experiment 4 – Full script:

from mininet.net import Mininet
from mininet.node import RemoteController, OVSSwitch
from mininet.link import TCLink
from mininet.cli import CLI
from mininet.log import setLogLevel
from mytopo import MyTopo
setLogLevel('info')
net = Mininet(topo=MyTopo(), switch=OVSSwitch, link=TCLink,
  controller=lambda n: RemoteController(n, ip='127.0.0.1', port=6653))
net.start(); net.pingAll()
h1, h4 = net.get('h1','h4')
net.iperf((h1, h4))   # limited by 10 Mbit/s s1-s2 link
CLI(net); net.stop()

Experiment 5 – Link failure: use a topology with two paths and a controller doing topology discovery (ONOS, or POX with openflow.discovery + openflow.spanning_tree). Run a continuous ping, then link s1 s2 down. The switch sends a Port-Status message, the controller recomputes paths and installs new flows. The gap in pings = recovery time.

5.8 Advantages & limitations

Advantages
  • Starts in seconds
  • Hundreds of nodes on one machine
  • Real apps, OVS, controllers
  • Python API, repeatable
  • Free, open source
Limitations
  • One shared kernel (no Windows hosts)
  • Limited by one machine’s CPU/memory
  • Timing inexact under load
  • No ASIC/TCAM limits modelled
  • Huge networks need cluster mode
Lab-viva tip: know what pingall, iperf, dump, net, ovs-ofctl dump-flows print, and that sudo mn -c fixes “file exists” errors after a crash.

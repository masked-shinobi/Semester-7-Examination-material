SDN Unit 4 – Deployments, Applications & Use Cases

A plain-English guide. Every hard word is explained the first time it appears, with a real-life example where helpful. Read top to bottom once; nothing from the unit is skipped.

Start here – SDN in one minute. In an old network every switch/router decides by itself where to send data (like every traffic police officer making up his own rules). In Software Defined Networking (SDN) the thinking is moved to one central brain, the controller (software). Switches just follow its instructions. The instructions are called flow rules: “if a packet looks like THIS, do THAT.”
Control plane = the brain (decides). Data plane = the muscles (forward packets). API = a way for programs to talk to each other. Northbound = controller ↔ apps above it; southbound = controller ↔ switches below it (e.g. OpenFlow).

TOPIC I

SDN in the Data Center

A data center (DC) is a huge building full of servers, storage and switches that runs websites, apps and clouds (think Google, Amazon, Azure). Its network must be fast, big, shared safely and automatic.

1. Why data centers need SDN (the problems)

Multi-tenancy
Many customers (“tenants”) share the same hardware but each wants a private network. A VLAN is an old way to separate networks but its ID is only 12 bits → just 4094 usable networks. Too few for a cloud.
Example One apartment building, thousands of families; each needs its own locked flat, but the building only has 4094 door keys.
VM mobility
A virtual machine (VM) is a “fake computer” running inside a real server. It can be moved live to another server (live migration). Its address, rules and paths must follow it with no manual work.
East–west traffic
Most traffic goes server ↔ server inside the data center (storage, big-data jobs), not out to the Internet.
STP limits
Spanning Tree Protocol avoids loops by switching OFF extra links → wasted capacity.
Scale & speed
Tens of thousands of ports; typing commands (CLI) box by box is impossible.
Small flow tables
TCAM is the special fast memory that stores rules in a switch. It is expensive and small, so rules must be planned carefully.

2. Topologies: three-tier vs leaf–spine

Three-tier (access → aggregation → core) is old, jammed at the top (“oversubscribed”) and needs STP. Leaf–spine (Clos) is modern: every leaf switch (top-of-rack, ToR, sits on top of a server rack) connects to every spine switch. So any two servers are the same number of hops apart, and all links are used. ECMP (Equal-Cost Multi-Path) spreads traffic across the equal paths.

AspectThree-tierLeaf–spine
LoopsSTP blocks linksRouted, all links active
East–westUneven, oversubscribedSame hop count, ECMP
GrowthBuy bigger boxes (scale up)Add more leaves/spines (scale out)
SDN fitLimitedExcellent – regular, easy to program
Fat-tree (a leaf-spine variant): with k-port switches: k pods, (k/2)² core switches, k³/4 hosts. For k = 48 → 27,648 hosts using cheap identical switches.

3. Network virtualization with overlays

The real physical network is the underlay. On top of it, software builds a private virtual network for each tenant: the overlay, using tunnels made by the virtual switch inside each server.

Example Overlay = putting your private letter inside an envelope and posting it. The postal system (underlay) only reads the outer address; the inner letter is your tenant’s own frame.

VXLAN (Virtual eXtensible LAN) wraps the VM’s Ethernet frame inside a UDP packet (port 4789) and adds a 24-bit VNI (network ID) → ~16 million networks instead of 4094. The tunnel ends are VTEPs, usually inside Open vSwitch (OVS) (a software switch) on each server. Extra header ≈ 50 bytes, so the underlay MTU (max packet size) must be increased.

4. SDN architecture in a data center

A tenant asks the cloud (OpenStack) to “create a network”. OpenStack’s Neutron service passes it through a plug-in (ML2 driver) to the SDN controller (ONOS or OpenDaylight). The controller then configures OVS on every compute node via OpenFlow and OVSDB, and configures the physical leaf/spine switches (OpenFlow/NETCONF).

5. What SDN does inside the data center

  1. Tenant isolation & micro-segmentation – a firewall rule per VM at the virtual switch, so even VMs of one tenant on one subnet can be separated.
  2. Traffic engineering & load balancing – ECMP can put several “elephant flows” (huge long transfers) on one link. Hedera spots them using switch statistics and moves them to empty paths.
  3. VM migration support – when a VM moves, the controller updates tunnels and rules.
  4. Fast provisioning – a tenant network in seconds by API, not days by CLI.
  5. Failure handling – controller recomputes paths; fast-failover group tables give instant local backup.
  6. Telemetry – flow/port counters feed monitoring and capacity planning.

Reactive vs proactive rules

Reactive: first packet goes to the controller, controller installs a rule. Adds delay + controller load.
Proactive: rules pushed before traffic. No delay. Data centers use proactive base rules (routing, tunnels) and reactive only for rare cases. Wildcard rules and aggregation save TCAM.
Example Reactive = asking the manager every time a new customer arrives. Proactive = giving the staff a rule book in the morning.

7. Challenges

Controller scalability/availability (fix: clustering) · limited hardware table size and flow-setup rate · hard to correlate overlay and underlay problems · integration with legacy networks and staff skills.
Exam tip Always pair overlay (VXLAN, tenant view) with underlay (leaf–spine IP fabric). SDN programs the overlay at the vSwitch.
TOPIC II

SDN in Other Environments

SDN is not only for data centers. Same idea everywhere: central brain + open interfaces. Answer pattern: legacy problem → SDN idea → example → benefit.

1. Wide Area Networks (WAN) and SD-WAN

A WAN links far-apart sites. Links are costly and set up router by router.

Google B4 – first famous SDN WAN. Links Google’s data centers with custom OpenFlow switches and a central traffic-engineering (TE) app. Links run at much higher utilization; controller reroutes after failures.
SD-WAN brings this to companies. An SD-WAN edge box at each branch builds encrypted tunnels over any mix of MPLS (expensive private line), broadband Internet and 4G/5G. A central orchestrator sends policy and does Zero-Touch Provisioning (ZTP) – ship the box, plug it in, it configures itself.
Application-aware routing: voice → lowest-delay link; backups → cheapest. Security can be chained at edge or cloud. Benefits: cheaper than all-MPLS, fast setup, central visibility.

2. Campus and enterprise

Campuses have BYOD (Bring Your Own Device), guests, IoT devices and strict security. The controller authenticates the user, gives a role, and installs matching rules on switches and Wi-Fi access points. Policy follows the user, not the port; an infected device is quarantined centrally. Early research used Mininet labs and OpenFlow campus switches at universities.

3. Wireless and mobile

Software-defined WLAN – Odin. Each client’s connection is a light virtual access point (LVAP) that the controller can move between physical access points → seamless handover + central policy.
Example Your phone “walks” from one Wi-Fi box to another and the call doesn’t drop, because the controller moves your virtual AP.
5G core – CUPS (Control and User Plane Separation). The SMF (control) programs the UPF (forwards user data; can sit near the edge). RAN = radio part (gNB made of CU/DU/RU). O-RAN adds RICs: non-real-time RIC (loops > 1 s, policies, AI/ML) and near-real-time RIC (10 ms–1 s) hosting xApps that tune the radio via the E2 interface.

4. Optical transport

Long-distance traffic rides on light colours (wavelengths) switched by ROADMs. Transport SDN lets a controller set up lightpaths, restore them after fibre cuts, and coordinate with the packet layer (packet–optical integration). Vendor-neutral models: ONF TAPI and OpenROADM; ONOS has optical apps.

5. IoT and sensor networks

Sensors are tiny and topology changes. SDN-WISE keeps nodes dumb (just match packets and apply rules) while a controller defines routing, duty cycles (sleep/wake times) and data aggregation. In bigger IoT, SDN gateways/edge controllers segment device classes and apply per-device policy.

6. Internet exchange points (IXP) and ISPs

SDX – BGP (the Internet’s routing protocol) forwards only by destination. At an SDX, members write application-specific policy (“send web traffic via peer X”); the controller turns it into OpenFlow rules while respecting BGP.
SDN-IP (ONOS) – lets an SDN network swap BGP routes with outside networks as if it were one ordinary network.
CORD (Central Office Re-architected as a Datacenter) – replaces telecom-exchange hardware with commodity servers, white-box switches and SDN/NFV software (e.g. virtual broadband access).

7. Multi-domain control and challenges

A parent orchestrator sits above domain controllers, each speaking its domain’s protocols (OpenFlow, NETCONF, gNMI, SNMP, vendor APIs). Benefit: uniform policy across mixed networks.

ChallengeMeaning
HeterogeneityDifferent devices, vendors, protocols
ScalabilityLarge spread-out networks need many controllers
LatencyWAN delay hurts reactive control
Security & trustInter-domain control exposes sensitive info
MigrationMust run alongside legacy gear (hybrid)
TOPIC III

SDN Applications

An SDN application is an ordinary program running above the controller. It uses the northbound API to watch and steer the network.

1. How an application works

Four steps: Subscribe to events (Packet-In, link up/down, host added, stats ready) → Learn state from controller services → Decide using its policy → Program rules/intents back. Reactive apps start from an event (Packet-In); proactive apps compute and install rules in advance.

2. Categories

(a) Traffic engineering & QoS
Pick least-loaded path, split across paths, reroute on failure, guarantee bandwidth with meters (rate limits) and queues. QoS = Quality of Service. Example: B4.
(b) Monitoring & telemetry
Read per-flow/port counters or use sFlow sampling; find elephant flows, congestion, anomalies. Every rule already counts packets/bytes – free data.
(c) Routing
Central path computation. SDN-IP talks BGP; segment routing puts the path as a stack of labels at the first switch; policy routing sends different apps on different paths.
(d) Load balancing
Server LB rewrites client traffic to a chosen server; path LB spreads flows over equal-cost routes (Unit 5 covers more).
(e) Security
Firewall, IDS redirection, DDoS mitigation, access control as flow rules (Unit 5).
(f) Virtualization & slicing
FlowVisor sits between switches and many controllers and gives each its own “slice” of traffic, so tenants/experiments share hardware.
(g) Energy saving
ElasticTree: at low load, pack flows on fewer links and switch off idle switches.
(h) Mobility
Update paths when a host/VM moves – seamless handover.
(i) Verification & debugging
VeriFlow and Header Space Analysis check rules before install (no loops, no black holes, isolation). Debuggers record packet histories.

3. A simple app: Ryu learning switch

Pattern of almost every reactive app. Ryu is a Python controller. Run: ryu-manager l2switch.py and connect Mininet with --controller remote.

  1. Table-miss rule: when a switch connects, install a lowest-priority rule “unknown packet → send to controller”.
  2. Packet-In: controller gets that packet.
  3. Learn: remember “source MAC X is on port P”.
  4. Decide: if destination MAC is known → that port; else flood (send out all ports).
  5. Install rule so later packets don’t come to the controller.
  6. Packet-Out: send this first packet on its way.
@set_ev_cls(EventOFPPacketIn, MAIN_DISPATCHER)
def on_packet_in(self, ev):
    table[eth.src] = in_port            # learn
    out = table.get(eth.dst, FLOOD)     # decide
    if out != FLOOD: add_flow(...)      # install rule
    send PacketOut(...)                 # forward first packet
Example Like a new receptionist: first time someone asks “where is Ravi?” she searches every room (flood), notes where she found him, and next time points directly.

6. Application life cycle

  1. Define requirement and events.
  2. Choose controller and API (Ryu Python, ONOS Java, REST).
  3. Develop and test in Mininet (network emulator).
  4. Verify rules and failure behaviour.
  5. Package, deploy, monitor with CI/CD (automatic build-test-release).
TOPIC IV

SDN Use Cases

A use case = a real problem + how SDN solves it. Answer in this order: context → problem → SDN design → benefit → limitation. In long answers give one deployed example and one limitation.

1. DC network virtualization
Problem: many tenants, moving VMs. SDN: controller-made overlays enforced in vSwitch; tenant policy as flow rules. Benefit: networks in seconds, millions of segments. Limit: must watch overlay + underlay together. Ex: OpenStack+ONOS/ODL, Azure.
2. WAN traffic engineering & bandwidth on demand
Problem: each router picks shortest path alone; links over-provisioned, capacity idle. SDN: controller collects demand + topology, allocates bandwidth by priority class, installs paths, reroutes on failure. Benefit: high utilization. Limit: controller must be highly available. Ex: B4. Bandwidth on demand: customer requests capacity for a time window; controller finds, programs and later releases the path.
3. Campus access & BYOD
Users log in (e.g. IEEE 802.1X), controller learns role, installs rules so students, staff, guests, IoT reach only allowed things; infected device isolated at once; policy written once for whole campus. Limit: identity integration.
4. Service providers: CORD & vCPE
Telecom central office becomes a small data center: ONOS controls a leaf–spine fabric of white-box (generic, open) switches; NFV (Network Function Virtualization – network boxes as software) hosts virtual functions such as a virtual Broadband Network Gateway; vCPE moves home-router functions into the operator’s cloud. New services by software. Limit: VNF performance.
5. DDoS mitigation
A DDoS floods a target with traffic from many machines. Edge switch counters → detector notices abnormal rates/spoofed sources → controller drops, rate-limits, or diverts to a scrubbing device (cleaner) while clean traffic continues. Automatic, in seconds. Limit: false positives.
6. Network visibility
Old: TAP (physical tap) and SPAN (port mirror) plus costly packet brokers. SDN: add rules to mirror chosen flows to analysis tools, change anytime, no re-cabling. Limit: mirror load on switches.
7. Service function chaining (SFC)
Traffic must pass ordered functions e.g. firewall → DPI (deep packet inspection) → NAT (address translation). Controller steers flows through the chain by rules or NSH header; chains per customer without rewiring.
8. Research & education
GENI (US testbed, OpenFlow slices), Internet2 (research network), OF@TEIN (Asia–Pacific OpenFlow testbed), Mininet (cheap classroom emulation).
9. Others
5G slicing/edge (transport + user plane per slice) · disaster recovery/cloud bursting (extend networks between sites, reroute on failure) · industrial/smart-grid (separate control traffic).

TOPIC V

ONOS – Open Network Operating System

ONOS is an open-source SDN controller built as a distributed network operating system. (Unit 3 covers installing it; here we learn the ideas.)

1. The network OS idea

Your computer’s OS hides hardware details and gives apps files, processes, devices. A Network OS (NOS) hides device details and gives apps topology, host and flow views, so apps needn’t speak every device protocol. NOX (first OpenFlow controller) introduced this; ONIX and later controllers made it distributed.

2. History and governance

Created by ON.Lab (Open Networking Laboratory); first release (“Avocet”) December 2014; joined the Linux Foundation in 2015; ONF carried it forward. In 2024 ONF merged its SDN projects into the Linux Foundation, so ONOS and OpenDaylight now sit in the same family.

3. Design goals

High availability – cluster; if a node fails others continue.
Scalability & performance – big networks, thousands of events/s, low latency.
Protocol independence – OpenFlow, P4Runtime, NETCONF, gNMI via providers.
Modularity – Java on Apache Karaf (OSGi): install/remove apps at run time.
Northbound abstractions – intents and flow objectives hide device detail.

4. Distributed architecture

Every ONOS node runs identical software. Each switch connects to several nodes but has exactly one master (others standby). State is shared through stores on Atomix: data needing strict agreement (mastership, intents) uses the Raft consensus protocol (nodes vote); topology can use eventually consistent replication (faster). Result: one logical network view across nodes.

ConcernHow ONOS handles it
Single point of failureCluster of 3 or 5 nodes, mastership failover
ConsistencyStrong for critical data, eventual for topology
LoadSwitches spread over nodes by mastership
UpgradesRolling upgrade of nodes

5. Subsystem pattern: Service – Manager – Store – Provider

Every subsystem (Device, Link, Host, Flow rule, Intent…) has: service (what apps call), manager (logic), store (distributed state), provider (talks protocol to devices). Changes raise events that apps get through listeners. Replaceable providers = protocol independent core.

6. Core abstractions

AbstractionMeaning
Device, Port, LinkNetwork elements and connections (links found with LLDP)
HostEnd system learned from ARP/DHCP: MAC, IP, attachment point
Flow ruleDevice-specific match–action entry
Flow objectiveDevice-independent goal: filtering (what to accept), forwarding (what to do on match), next (how to forward onward). A driver translates it for a specific switch pipeline
Group / MeterShared action buckets (multicast, failover) / rate limiters
IntentHigh-level “what, not how” request; ONOS compiles it to flow rules and keeps it satisfied after failures
Topology / PathGraph of devices and links to compute routes
Example Intent = telling a taxi app “take me to the airport”. It picks the route and re-routes if a road closes. Flow rules = giving the driver every turn.

Intent life cycle: submitted → compiling → installing → installed; if a link fails it is recompiled automatically; it ends withdrawn or failed.

7. Southbound and northbound

Southbound providers: OpenFlow, P4Runtime, NETCONF, gNMI, OVSDB, BGP, SNMP; drivers describe device behaviour. Northbound: REST API, gRPC, web GUI, CLI, intent framework.
